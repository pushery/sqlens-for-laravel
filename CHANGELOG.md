# Changelog

All notable changes to `pushery/sqlens-for-laravel` are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.0.0/) and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.23.0] - 2026-09-21

### Added

- **Five undetermined answers named a reason that describes a different state — four new reasons, and `unknown_server_version` now says what it covers.** A consumer branches on the reason, so a reason whose own description sends the reader somewhere else is a wrong answer, even beside a correct sentence. `SEC.CFG.TLS_MIN_VERSION` reported a TLS version name this build has never measured as `unsupported_engine`, about a fully supported PostgreSQL. It now reports `setting_value_unrecognized`, and so does `SEC.CFG.PATCH_EOL` for a version string it cannot read as a release series, which used to say `unknown_server_version`. **The difference is the remedy, not the wording**: `unknown_server_version` is a run with no version to reason from, and `assume_server_version` answers it. These two checks judge the live value, so a pin changes nothing, and the server, which accepted the value, is not what needs fixing. `SEC.PII.UNENCRYPTED_COLUMN` in a run assembled without the model reading reported `model_not_found`, which sends a reader to the application's models when no model was looked for; it now reports `model_reading_not_wired`. `SEC.PRIV.CONNECTIONS_UNSEPARATED` with both connections named and their credentials unreadable in the run reported `not_configured`, whose own definition is a setting the project has not made; it now reports `connection_identity_unresolved`. `SEC.AUTH.HBA_PARSE_ERROR` over an authentication-rule reading that came back empty without refusing reported `catalog_read_failed`, the catch-all for an unanticipated error that carries an error code; it now reports `catalog_reading_implausible`. `unknown_server_version` itself stays one reason for an absent and an unreadable version banner, because a pin answers both, and its description now says so. **A consumer branching on the old value for any of these five will stop matching** and should read the new one. As with the last reason added, the reason set is not part of the versioned run-field register, so the report schema does not move.

### Fixed

- **A published config that still carries `mode` stopped every command — and the 0.20.0 notes said it would not.** 0.20.0 removed the key with the sentence *„a published config that still carries it gets a notice rather than a refusal“* and shipped the refusal: nothing told a key this package retired from a key it never had, so `mode` fell into the unknown-key path and every `sqlens:*` command exited on misconfiguration. **It stopped green, which is the part that matters:** a package that runs nothing raises no red line, so a project that upgraded lost its checks without a signal. A retired key is now named, ignored, and the run continues — under a header of its own, because the key is SET, while the notice for a defaulted key tells a reader to RE-ADD what is missing and would have told this one to restore the line it should delete. `sqlens:doctor` reports it as `retired`, in the console and under a new `config.retired` list in `--format=json`, where every notice used to read `absent`. **An unknown key is still fatal, deliberately.** The retired keys are a list, not a pattern: a key one letter away from `mode` is refused exactly as before, because the typo protection is the half of this validator that was always doing the work. **Delete `mode` from your published config** — nothing has read it since 0.20.0.

- **On a managed MySQL, a grant on a database or table whose name contains a space was dropped from the security reading, and a grant to a user whose name contains one was filed under an account that does not exist.** When the grant tables are refused — the ordinary case on a managed server — the reading falls back to `SHOW GRANTS` for the connecting account, and it parsed each line with a pattern whose identifiers were `\S+`. MySQL writes identifiers in backticks and allows a space inside them. Measured on 8.4.10: a grant on a database named `my app` matched nothing and was taken for a role membership, so the grant vanished and the rules reading it reported clean; a grant to a user named `app user` matched with the grantee cut at the space. **Widening `\S+` would not have been enough:** a backticked name may also carry a comma, a parenthesis, a doubled backtick, or the words `ON` and `TO`, and a pattern anchored on those words reads the wrong one. Each line is now split by its structure, with backticked names opaque and the keywords recognized only outside them. A GRANT that carries an ON and still does not parse is named as a skip rather than dropped.

- **The cross-source dedupe layer's header now says what it can and cannot pair, and why a migration's grant and the live grant stay two findings.** It said the rule id was *„the only thing two such findings are guaranteed to share“*. It is not a guarantee — it is the first of **three** mismatches, measured over the whole `SEC.PRIV.*` family, 7 migration-side rules against 15 catalog-side ones. The ids differ by construction (the migration side carries an `_IN_MIGRATION` suffix). The object type is the harder half: not one of the 7 declares `judgedObjectTypes()`, so each takes the fallback and names the statement's subject **table**, while its catalog counterpart judges a `Grant` or a `Role`, and the object name follows from that. The 0.22.0 notes said such a pair "still cannot meet". It will not be made to: the migration half of `sqlens:security` judges pending migrations, so a pending `GRANT … TO PUBLIC` is the next deploy granting it again rather than the live grant reported twice. The two findings carry two remedies, revoking the grant and changing the migration, and suppressing one as the other would hide that the revoke does not survive the next deploy.

- **Shipped prose named rule ids this package has never had, and a guard now reads them.** The published `config/sqlens.php` and a shipped comment said `SEC.PRIV.GRANT_TO_PUBLIC`; the rule is `SEC.PRIV.GRANT_PUBLIC`. The config comment is the one a project copies when it publishes the file, so a copy made earlier still carries the wrong name and is worth correcting by hand. Three more comments said `PG.L7.REDUNDANT_INDEX` for `PG.L7.INDEX_REDUNDANT`, `PG.L6.PK.UUID_V4` for `PG.L6.PK_UUID_V4`, and `MY.L1.SQL_MODE` for a family that sits at levels 5 and 6. No check read rule ids out of prose before — the ones that existed cover the ignore list, the MCP answer and the documentation pages, all of which take an id as *input*. A guard now reads every rule-id-shaped token in `src/` and `config/` against the shipped registry, whole rather than up to its third segment, so the next one fails the build instead of reaching a reader.

- **The MySQL DDL-privilege artifact now says why `CREATE ROLE` and `DROP ROLE` are not structural, and a guard reconciles it against the server in the direction that was missing.** Both were always handled correctly — they are administration of the server and are reported by `SEC.PRIV.GRANT_SERVER_ADMIN` — but `deliberately_absent` named their neighbor `CREATE USER` and not them, so re-checking the list against a new server meant opening another rule's vocabulary to learn why two names were missing. The existing check proved every name in the artifact is one the server grants; the new one proves the reverse against `SHOW PRIVILEGES`: every privilege the server names after the DDL it permits is listed, explained, or mapped to a canonical case — without a fourth file.

- **A regular-expression result is never read as a bare condition any more, and the one place that folded the engine giving up into a count of zero now reads it as unknown.** `preg_match()` answers `1`, `0` — or `false` when the engine gives up on a subject — and under `!`, `if (…)` or a cast the last two become one branch, so a subject nobody judged is handled like one judged and rejected. A guard now reads every call in the shipped tree and refuses that form. It found a second site, which a search for bare conditions walks past because it is not one: the placeholder count behind the binding check added `(int) preg_match_all(…)`, so an engine that gave up counted as zero named placeholders. That is an under-count, the one direction the count must not err in, since zero can agree with an empty binding list and pass. It now answers a count no binding list can match, which the comparison reads as the mismatch it is.

- **On PostgreSQL, one table had as many canonical forms as it had unquoted spellings — `CREATE TABLE Orders` and `CREATE TABLE "orders"` now canonicalize alike.** PostgreSQL folds every unquoted name to lower case before anything reads it, so both statements create the same table, and the canonical form kept `Orders` as written: the stage that knows the keywords left every other word alone, and the stage before it leaves a standalone bare word to that one. The fold now happens where the keywords are known, per driver. PostgreSQL lower-cases a bare word that is not a keyword, and a QUOTED `"Orders"` stays distinct, because on PostgreSQL it is a different table. MySQL is deliberately not folded: whether `Orders` and `orders` are one table there depends on `lower_case_table_names`, which is case-sensitive on Linux. The fold is ASCII only, in a qualified name as much as in a bare one, because that is what PostgreSQL does in a UTF-8 database: `create table Élan` creates `Élan`. A qualified name used to fold the `É` as well, so `Élan` and `"élan"`, two tables, shared a canonical form. **The canonical form version moves to 5**, and with it every statement fingerprint, because the version is part of the hash. **A committed baseline is not affected, and it never was.** Its entries are keyed by rule and location; the statement fingerprint every producer hands `FindingFingerprint` has been empty since the baseline command existed. The 0.21.0 notes said the opposite for form 4 — that every baseline entry gets a new identity and a project regenerates its baseline once — and so did the canonical-form page. Both were wrong, and following them does harm: a regenerated baseline re-accepts whatever is reported at that moment, new findings included. The page now says what the code does, and there is nothing to regenerate for this bump either.

## [0.22.0] - 2026-09-21

### Added

- ⚠️ **A known server version with no matrix row no longer reports `unknown_server_version` — new reason `setting_expectation_missing`.** Every setting rule answered `undetermined` with the same reason for two different situations, because `ServerSettingMatrix::for()` returns the same `null` for both: the version could not be resolved, and the version IS known while this package ships no expectation for that variable at it. ⚠️ **The two send an operator to different places**, which is why this is not a cosmetic rename — *„I do not know which server this is“* points at the version pin, *„I know the server and have nothing on file“* points at the matrix, or at us. Somebody with a correctly pinned server was told their version was the problem, and the sentence beside it said so too. Both sentences now name what is actually missing, and the version-known one prints the version, because which version had nothing on file is the fact a reader would otherwise have to guess. ⚠️ **A consumer branching on `unknown_server_version` for a settings finding will stop matching** and should read the new value instead; the reason set is not part of the versioned run-field register, so the report schema does not move for it. Both directions are pinned by arms that differ in one thing — whether the subject carries a version at all — because the pair is the claim and either half alone is satisfied by a rule that simply renamed one reason to the other.

- ⚠️ **SCHEMA VERSION 7: the run header names the day it judged on, as `run_day`.** Rules that judge on a date — a support window closing, a debt acknowledgment expiring — were reproducible only by luck at a boundary: the report named no day, so re-examining a verdict across midnight meant guessing which side the run had been on. The clock is read once per run and handed to the rules **and** to this header, so the day in the report is the day that was judged on rather than a second reading that usually agrees. ⚠️ **It is a new schema version and not a field on 6, and that is the whole cost:** a field added to a version consumers already hold would tell them they had it all along, and schema 6 shipped with 0.12.0. The version rise is classified `allowed_in_minor` by the package's own breaking-change detector, which says why in its code: every version names the fields it added in a register the envelope's tests hold against the number, so a rise is an addition by construction. ⚠️ **`run_day` is the LAST key of the header, and the position is contract rather than tidiness** — the register guard compares the post-v3 keys in header order, so a v7 field standing in front of a v6 one would announce itself to a consumer on schema 6. An arm asserts it is last and that the value traveled rather than being re-derived. ⚠️ **And the clock turned out to have SIX producers, not the four the design described:** three of them reach the header through the run-context collector, which reads like a configuration reader. A named arm now pins that exact set — a seventh entry is a seventh clock, and the collector itself must create none, because five producers call it once per run and a reading there would compete with the one the rules got. The announced-and-shipped check, which covered only version 4, now covers 5, 6 and 7: a register naming a field the header never carries reads like a promise, and only the union caught the other direction.

### Changed

- ⚠️ **BREAKING for a caller that constructs a driver or the driver registry with a date string: `$today` is now a `Today` value object.** Nothing in this package passed one — the service provider deliberately passes `null` — so the change is invisible to an ordinary install; a third-party caller that handed in a `Y-m-d` string updates one argument. The optional `AcceptsRunClock` interface is **additive**: a driver that does not implement it keeps the documented fallback of one clock reading per `rules()` call, which is what every driver did before, so no implementer breaks. ⚠️ **A required parameter on `Driver::rules()` was the obvious design and was measured and rejected:** two of that method's five callers only ENUMERATE rules — the shipped rule-registry artifact and the rule-id-to-operation-class map — and neither judges a database or has a „today“. A required parameter would force both to invent a date inside an artifact that is compared against a golden file, which is a non-deterministic artifact.

- ⚠️ **One clock per run, and there were FIVE readings.** `gmdate('Y-m-d')` was called wherever a day was needed: twice in the lint runner, twice in the audit runner, once in the postdeploy command. Each call is its own reading, so a run crossing midnight registered debt candidates against one calendar day and collected standings against another — inside one report, with nothing saying which side either was on. The two-clock defect the previous cycle fixed between two rule families existed **within a single debt pass** the whole time. Each run now reads the clock once, at its entry, and hands the value down; the shipped tree contains `gmdate('Y-m-d')` in exactly two places, and an arm names both rather than counting them. ⚠️ **The value is an OBJECT rather than the string it wraps**, because the property that has to be provable is identity and not equality: two readings agree on almost every run and differ exactly when it matters, so a string could only ever establish that two readers saw the same DAY. ⚠️ **And the anti-vacuity control of the existing guard had to be rewritten, because it was calibrated to the old COUNT** — `toBeGreaterThan(2)` over the files that read the clock, which turned red the moment those readings were consolidated. A control pinned to today's quantity fails on progress and passes on regression in the same breath; it now names the two files and says why each is allowed. ⚠️ **Both shipped drivers lose their class-level `readonly` and carry it per property instead**, which keeps every guarantee except on the one field the run clock sets: a readonly CLASS leaves a `with…()` method no field to write on PHP 8.4, and the 8.5 clone-with form that does is not available on the version this package promises. Caught by the integration gate rather than locally, because the development machine runs 8.5 — a local syntax check measures the machine, not the declared floor.

- ⚠️ **The `sqlens:agent-rules` block now says that it records no package version, and why — a consumer asked for one, and writing it would have cost every consumer a red integration branch per release.** `--check` compares the WHOLE generated content (`$desired !== $existing`), not the `catalog=` hash in the marker — so the suggested middle, *a version in the block but out of the hash*, does not exist: anything in the generated text arms the check. With in-house packages merging on an automatic update without a waiting period, a version line would turn `check-quality` red in every consuming project on every release of this package, until somebody re-ran the command. ⚠️ **A version-blind comparison is the other way out and this command refuses it in its own words**: check and write are one path, because two would agree until they did not. ⚠️ **And nothing is lost, which is why the line is a sentence rather than a field:** a green `--check` already establishes that the list matches the rule set of the version installed, and which version that is takes one `composer show`. What the sentence prevents is the failure actually measured in a consuming project — a hand-written version beside generated content, **12 of 14** markers reading `never` against an installed version three minors ahead, because prose outside the block is unguarded and exits 0 however wrong it is. An arm now pins the content-not-marker distinction by editing inside the block while leaving the marker line byte-identical; the three neighboring arms replace the file or the whole section, so none of them could tell the two apart. **Consumers regenerate once**, as with any change to the generated text.

### Fixed

- ⚠️ **The cross-source dedupe layer can finally fire, and `sqlens:security` can finally say what it hid.** The layer collapses "a migration grants to PUBLIC" and "the catalog holds that grant" into one report entry, and it had never once fired: `sqlens:security` resolves its two halves in separate passes with a resolver each, so a lint pass held no catalog candidate to build an entitlement set from and an audit pass returned early on every candidate. The audit half runs first anyway, so its **visible** findings now ride into the lint half. ⚠️ **Visible, not every audit finding, and that is the safety of the whole thing** — feeding the hidden ones too would let one baseline entry on the catalog side take the migration side down with it, and the fact would leave the report entirely: accepted in one place, erased in another. ⚠️ **And a second defect went with it, which consumers see directly:** `SecurityOutcome` carried finding lists only, so `suppressed_by_source` in the `sqlens:security` report was a **permanent zero** — which reads as "nothing was hidden" rather than as "this report cannot tell you". Both halves hand their book up now and the aggregate concatenates it; each entry was made exactly once by exactly one half, over disjoint candidate sets, so `sqlens:audit` on its own keeps the count it always had. ⚠️ **This is necessary and not sufficient, and that is measured rather than suspected:** `identity()` includes the rule id, and the two sides of one risk are named differently (`SEC.PRIV.GRANT_PUBLIC_IN_MIGRATION` against `SEC.PRIV.GRANT_PUBLIC`). Across all 21 rules, zero run in both suites and exactly one of the eight `_IN_MIGRATION` ids has a twin — so a real pair still cannot meet, and the arms covering this say so in their own header rather than reading as proof of a working collapse.

- ⚠️ **`PG.L4.ENUM_ADD_VALUE` told a reader to add an enum value the migration never names.** The capture read the added value with `'([^']*)'`, which ends at the FIRST quote — and a quote inside a PostgreSQL literal is written by doubling it, which is the grammar rather than an edge case. Measured: `ALTER TYPE mood ADD VALUE 'it''s fine'` came back as `it`, and `'a''b''c'` as `a`. ⚠️ **The damage is that it was a WRONG answer and not a missing one.** The class docblock promises that a shape the pattern does not recognize leaves the placeholder standing *„rather than guessing at a literal“* — but the pattern MATCHED, so the truncated text counted as established and the remediation printed it as the value to add. The form now used is the one `IndexPredicate::LITERAL` already carries and documents with the same example, and the value is un-doubled on the way out. ⚠️ **And the promise itself is now asserted**, which it never was: an unquoted value returns `null` while the addition is still recognized, so a reader who writes something this class cannot parse gets a placeholder instead of an invention. That missing arm is how the truncation survived — a promise no arm checks is a comment. Nine arms, including both edge doublings, both `IF NOT EXISTS` forms, and an anti-vacuity control, because every value arm reaches through `?->` and an `of()` that returned null for everything would leave all of them green.

- ⚠️ **`DEPLOY.PREFLIGHT.FREEZE_HORIZON` told a deploy no anti-wraparound vacuum was running, from a session that could not have seen one.** PostgreSQL does not REFUSE `pg_stat_activity` to a role without `pg_read_all_stats` — it **masks** the foreign rows. So `query` reads `<insufficient privilege>`, the filter that recognizes a worker by its query text matches nothing, the read succeeds, and nothing throws: the check's `catch` never fired and the result was a clean pass. Measured on 18.4 with a role holding only CONNECT: two foreign sessions, both masked, zero rows through the vacuum filter, no exception. ⚠️ **The condition is not exotic — a least-privilege migration role is exactly what this package's own `SEC.PRIV.*` rules recommend**, so following that advice cost this check silently. The visibility is now asked before the emptiness is interpreted, with `pg_has_role` on `pg_read_all_stats` rather than `has_table_privilege` on the view: the question is not whether the view may be read, which it may, but whether foreign sessions appear in it. ⚠️ **It is an `undetermined` on ONE axis, not a shutdown.** The age clocks come from `pg_class` and are readable by anybody, so a table near its horizon is still reported as a finding; only the case that used to be a *pass* — nothing near, nothing visibly running — becomes undetermined, and the sentence says which half was answered. The probe is asked only in that case, because a query bought for an answer nobody reads is a query on somebody's production instance at the moment before a deploy. Proven against a real role, created and dropped by the test, one `grant pg_read_all_stats` apart from its own positive control. ⚠️ **And a neighboring suspicion was measured and REFUTED rather than built:** `backend_type` for a masked session is **NULL**, not an empty string, so `PgsqlActivityReader`'s existing `backend_type is null` filter is correct and passes 2 of 2 masked rows — changing it to compare against `''` would have dropped the filter to zero rows and defeated the masking detector with the masking it counts. The earlier probe had *rendered* the value, and a NULL prints as an empty string.

- ⚠️ **An ordinary index takes four column operations off their pinned fast path, and the online-DDL matrix named only the FUNCTIONAL one.** Measured on 8.4.10 with the algorithm pinned, each operation run twice differing in nothing but a plain `KEY`: dropping a plain column, a stored generated column and a virtual generated column are all accepted `ALGORITHM=INSTANT` unindexed and **refused with error 1845** once indexed; a `utf8mb3 → utf8mb4` column change is accepted `ALGORITHM=INPLACE, LOCK=NONE` unindexed and **refused with 1846** once indexed. The statement does not fall back and run slowly — it fails, so a pinned migration breaks rather than drags. ⚠️ **The control is what makes the charset row mean anything:** that entry already refuses `latin1 → utf8mb4` with the same 1846, because the stored bytes change — so the arm fires that condition on an *unindexed* column, and the pair chosen for the index rows changes no stored byte at all. ⚠️ **The scope came from the measurement rather than from the report:** two operations were reported, the probe was pointed at all three entries carrying the functional-index condition, and two more refuse identically. Nothing beyond what was measured carries the new condition, and an arm pins that list in both directions. ⚠️ **And the entry's own `rebuilds_table: false` is conditional on the pin**, which the same run showed: without `ALGORITHM=INSTANT` the drop rebuilds the table. That is compatible with the package's model — the remediation tells you to pin — but it is now said in the notes, because a migration that does not pin gets exactly the cost the entry rules out. ⚠️ **Decided toward a condition rather than a pessimistic reclassification**, against the precedent set for `convert_character_set`: measured, both entries already resolve to `undetermined` on the shipped path, because `MatrixContext::blind()` decides nothing and 13 of the 50 entries carry conditions. The feared cost of a condition is therefore already paid, while a pessimistic axis would replace an honest "I do not know" with a definite claim that is wrong whenever the column is unindexed.

- ⚠️ **`PG.L2.TYPE_CHANGE_REWRITE` warned about an outage that a project following this package's own advice does not get.** Since PostgreSQL 12 an `ALTER COLUMN … TYPE timestamptz` is metadata-only when the session's `TimeZone` is UTC, and a rewrite otherwise — and `PG.L6.TIMEZONE_NOT_UTC` is the rule that tells a project to run on UTC. The type-change matrix classifies by the target's **dominant real case**, which it says of itself; for this one target the dominant case is the free one, and we are the reason. Measured against 18.4 with `relfilenode` as the signal: UTC no rewrite at 0.7 ms, `Europe/Berlin` a rewrite at 25.9 ms, the two runs differing in nothing but the session setting — with controls in both directions (`int → bigint` rewrote, `varchar(10) → varchar(20)` did not), because a reading of "no rewrite" is exactly what a broken detector produces. **Both directions carry it**: `timestamptz → timestamp` under UTC is free as well, which the ticket had not named. ⚠️ **The wording is the whole risk and is deliberate.** A heuristic that names its exception is easier to wave away — someone not on UTC reads "this may not apply" and stops. So the finding does not offer an excuse, it hands over the decision procedure: `SHOW TimeZone;` in the session that will run the migration. A caveat you can answer in a second is not an invitation to skip the check; an unanswerable one is. The finding still prints the ACCESS EXCLUSIVE warning, and an arm holds that an unconditional target such as `bigint` gets no such caveat — otherwise the fix would teach a reader to skim every rewrite finding. ⚠️ **The definitive answer belongs to the audit suite**, which has a connection and could simply read `TimeZone`; it is not built here because the rule receives no server state at all, and handing a rule runtime state would be the first time any rule receives it — that seam does not exist yet.

## [0.21.0] - 2026-09-20

### Added

- ⚠️ **CANONICAL FORM VERSION 4, and every fingerprint changes with it — read this before upgrading.** `ALWAYS`, `GENERATED`, `STORED` and `VIRTUAL` were in neither driver's keyword list, so `generated always as identity` folded only its `AS`: the same DDL in two casings produced two canonical strings, which is **two fingerprints for one statement** — the exact defect this package's canonicalization exists to prevent, in its own words. ⚠️ **The consequence is wider than the four words, and it is not a side effect but the design:** the form version is part of the canonical fingerprint, and `FindingFingerprint` folds that fingerprint in — so **every** baseline entry gets a new identity on this upgrade, not only entries about generated columns. A project with a baseline regenerates it once; accepted findings come back until it does. That is what a form bump has always meant here (forms 2 and 3 did the same), and the version exists so the change is announced rather than discovered. ⚠️ **Why these four slipped through is the same reason the query vocabulary did, recorded in that file twice already:** the keyword guard's corpus is generated from the SCHEMA builder, and `GENERATED ALWAYS AS IDENTITY` is written by hand or through `->change()`, never by the builder's ordinary path — so no corpus statement ever carried them. **Both engines**, because the MySQL list was measured rather than assumed and carried the identical gap; `VIRTUAL` and `STORED` are the commoner spellings there. The four words appear in no shipped rule pattern (measured, with a control), so nothing was ever mis-reported — what moved was the identity.

- ⚠️ **BREAKING, and small: `sqlens:doctor --strict` is now `--strict-tools`.** One flag name meant two things. `sqlens:audit --strict` treats an undetermined result as a failure — `strict_undetermined` — while doctor's asked whether a strict-**tools** run would fail: two config keys behind one name, on two commands a reader meets in the same session. `sqlens:lint`, `sqlens:security` and `sqlens:format` all spell the tools question `--strict-tools`, so doctor was the outlier and doctor is what moved. **No alias, deliberately** — an alias would keep exactly the ambiguity this removes, and `sqlens:doctor --strict` would still mean something different from `sqlens:audit --strict`. ⚠️ **The shipped agent skill already asserted the new state:** *"`--strict` is an audit option only"* was false while it read as true, and the rename is what makes it a fact. ⚠️ **A guard now holds the whole option surface to one meaning per name** — every option of every registered command must appear in a declared table exactly once, in both directions, so a name reused for a second meaning has nowhere to go and a new option cannot ship without somebody writing down what it is. Meaning is not in a signature, so the table is declared rather than derived, and the arm says so instead of implying otherwise.

- ⚠️ **`SEC.PRIV.PROXY_TO_ADMIN_IN_MIGRATION` — a migration that grants `PROXY` on the server's own account, which hands over every privilege of that account while naming none of them.** `GRANT PROXY` is not a privilege over data or over the server: it is permission to **connect as** another account, so the grantee authenticates with its own credential and then holds the proxied account's privileges instead of its own. `GRANT PROXY ON 'root'@'localhost' TO 'app'@'%'` is a root session for the application, and a review that reads privilege lists sees nothing in it. **The shipped registry holds 241 entries**, one more than 0.20.0. By category: 145 safety, 59 security, 17 idiom, 10 performance, 7 convention and 3 privacy. By maturity: 236 stable, 3 preview, 2 experimental. **160** answer to the level gate; the other **81** carry a severity — 7 critical, 33 high, 29 medium, 8 low and 4 info. It carries no `downtime_class` — a grant is not an operation on a schema — so that count stays at 58 entries. ⚠️ **It needed its own rule because of GRAMMAR, not because of area.** `PROXY` reads as administrative — 8.4 reports it under `Context = 'Server Admin'` — and the obvious move was a row in the administrative-privilege artifact. That artifact describes names appearing in a `GRANT … ON *.*` shape, and `PROXY` takes an **account** as its object: `GRANT PROXY ON *.*` is rejected with `ERROR 1064`, measured. An entry there could never have matched, and the arm that offers every listed name to a real server would have stayed red forever — which is how this was found. It sits in that artifact's excluded set now, pointing at the rule. ⚠️ **It judges the TARGET, and a rule reporting the shape would have been switched off in a week.** Proxying is a legitimate authentication arrangement, and measured on 8.4.10 a stock server ships one of its own accord: `root@localhost -> ''@''` sits in `mysql.proxies_priv` on a fresh install. So the rule fires on an administrative **proxied** account — the `mysql.` prefix the server uses for its own, and `root` — and the `good` fixture keeps the mechanism rather than removing it. ⚠️ **What it cannot see is declared rather than left to be discovered:** an arbitrary privileged account such as `admin@%` is invisible, because a statement does not say what an account holds; that question needs the catalog. `root` is a convention rather than a reserved name, so a renamed one is not reported. And the severity does not vary with the target — `mysql.infoschema` carries no `SUPER` where `mysql.session` does, and both report at High, because a project account should be impersonating neither. Silent on PostgreSQL by grammar: it has no `GRANT PROXY`, and that exemption is declared in the fixture allowlist rather than left as a missing file.

- ⚠️ **`Driver::readers()` is removed from the driver contract, which is a breaking change for a third-party driver — and it is the second time this was found.** The method sat on the contract for eight months answering `[]` from both shipped drivers, with no caller anywhere in the source: the live-catalog readers come from `CatalogReaderFactory`, which describes itself as *"the ONE place that knows which engine gets which"*. `Driver` calls itself the extension API third-party rule packs implement, so a method nothing reads costs an implementer a decision, a stub and a docblock and returns nothing for any of it. ⚠️ **A test pinned the emptiness**, which is what made it read as deliberate rather than dead — a documented intermediate state on the way to being filled. What replaces it guards the general form instead of that one method: every method the contract declares has a caller in the shipped source, read out of the interface by reflection so a method added tomorrow is covered too. **A third-party driver removes its own `readers()` stub; nothing else changes.** The `rules()` docblock is rewritten in the same pass — it still said *"Empty for now, filled later by the PostgreSQL and MySQL rule packs"* while the PostgreSQL driver contributes 108 rules and the MySQL one 100. A sentence describing an intermediate state has to be retired when the state is left, or it starts describing the reader's expectations instead of the code.

- **`sqlens:doctor` reports what the configuration validator found; it does not refuse on it.** Every other command stops, because a key this package does not know is a key it **ignores** and ignoring is silent. This one describes an environment, and an operator reaches for it precisely when something is off — a doctor that will not start because the configuration is broken has inverted its own purpose, and its suite has said so since long before the validator arrived there: *"it DESCRIBES a broken profile rather than dying on it, the one command that must survive it"*. The console report gains a line per violated key and the JSON document a `config` section carrying `status`, the violations and the notices. ⚠️ **`status` is present when everything is fine too**, for the same reason the guard section reports `off` as a value rather than an absence: a field that appears only when something is wrong answers "is my configuration alright?" with silence, and silence reads exactly like a doctor that never looked. Nothing is lost by reporting instead of refusing — a run that *matters* still stops, at whichever command was going to do the work.

- **`sqlens:postdeploy` resolves a profile like every other suite command, instead of announcing one it never looked up.** `--profile=postdeploy` was an option default, and `postdeploy` is not a profile: there is no such enum case and no such block under `sqlens.profiles`, so the name could not have selected anything even if something had tried. Three consequences, all gone: `SQLENS_PROFILE=ci sqlens:postdeploy` ran as postdeploy with nothing saying so, though the configuration promises a name "outranks those defaults for every command"; `--profile=bogus` was accepted and written into every finding's subject, where every other command answers `Misconfiguration` and names the legal set; and the report contradicted itself, the header reading `local` while the findings underneath said `postdeploy`. **The default is now `predeploy`**, because this command runs in the deploy window one step after the gate that already uses it. On the shipped base that changes nothing — `predeploy` overrides only `security.min_severity`, to the value the base already carries — and what it buys is the reason `ci` and `predeploy` name that key at all: a project that lowers its base floor while working through a backlog no longer lowers this gate with it.

- **The MCP server's second transport check is gone, because it had become unreachable.** Its own comment predicted this: *"the configuration validator already refuses anything else, so reaching this means it was bypassed"* — a sentence that was false while the validator had no caller on that command, and true the moment it got one. What it did happens a step earlier and says more: the validator names the **key** and the legal value, where the old line only said which transport this build speaks, so a project with a typo'd `agent.mcp.transort` was told about stdio and never about the typo.

- **Every command checks the configuration before it does anything, not three of eleven.** A key this package does not know is a key it **ignores**, and ignoring is silent: a run with `levl: 3` uses the default level and comes back green because it checked less. The validator that catches this reached exactly the commands that write a report — a coincidence of where the method happened to live. The eight it missed are the ones where it matters most: `predeploy` and `postdeploy` run **inside the deploy window**, `baseline`, `drift` and `format` write files into the repository, and the MCP server binds tools to whatever the configuration says. Two of those carry comments asserting the validator has already refused the shape they are about to read — one justifies falling back on an unusable threshold that way, the other says reaching a branch "means it was bypassed". Neither sentence was true of the run. The check now lives in its own trait, self-sufficient rather than borrowing two helpers from two other traits, and a check over the service provider's own registration keeps a twelfth command from being added without it. ⚠️ **The arm asserts the message, not the exit code:** several of these answer with the misconfiguration exit for reasons of their own — an unreachable database, no migration paths — so an exit-code check was green on ten of eleven against a tree where nothing called the validator at all.

- **A configured baseline whose file is missing now says so, instead of reading as a baseline that accepts nothing.** The two produce an identical report and mean opposite things: one is a project with a clean slate, the other is a project whose accepted findings have all come back at once — and the reader sees a wall of new findings either way, with no reason given. Both runners now emit a run notice for it, `LINT.BASELINE.ABSENT` and `CAP.L0.BASELINE_ABSENT`, under the new undetermined reason `baseline_absent`. ⚠️ **A notice and not a refusal, deliberately:** `sqlens:baseline` has to be runnable before the file exists — that is how a project creates one — so a configured path with nothing behind it yet is an ordinary state on the way to having a baseline, and a project that knows that about itself can name the reason in `allow_undetermined`. The JSON envelope gains the new reason in its histogram, as every reason before it did; `schema_version` stays at 6. **The shipped registry holds 240 entries**, two more than 0.19.0 — both of them these notices. By category: **145 safety**, 58 security, 17 idiom, 10 performance, 7 convention and 3 privacy. By maturity: **235 stable**, 3 preview, 2 experimental. **160** answer to the level gate; the other **80** carry a severity — 7 critical, 32 high, 29 medium, 8 low and 4 info. Neither carries a `downtime_class` — a missing baseline file is not an operation on a schema — so that count stays at 58 entries.
- **The baseline is found where the configuration says it is, not where the process happened to start.** `sqlens.baseline.path` is documented as repo-relative and the schema refuses an absolute one, and it was then resolved against the **working directory**. That is the normal case rather than an exotic one: `php path/to/artisan` from a monorepo root, a deploy script that changed directory, a queue worker started by a daemon, `Artisan::call()` from a request where the working directory is `public/`. The three sibling keys carrying the same promise — the debt ledger in both runners, the agent's findings path — were already anchored at the application root; only this one was not. It fails in the quiet direction: the file is not found, the baseline reads as **empty**, every accepted finding comes back at once, and nothing says a baseline was configured. Writing had the mirror problem — `sqlens:baseline` created the file wherever the process was, outside the repository the relative path exists to keep it portable within. Both now resolve through one call. ⚠️ An **absolute** path is left alone: a configuration that slips past the validator must not then be read from a third place nobody named.

- **A `url`-configured connection is no longer half-supported.** Laravel runs every connection through `ConfigurationUrlParser`, so `'url' => 'pgsql://…'` **has** a driver — derived from the scheme — while `database.connections.<name>.driver` is simply absent. That is the shape Laravel Cloud, Heroku and every `DATABASE_URL` deployment produce, and nine readers in this package read the key raw. The user-visible symptom was the confusing one: `sqlens:lint`, `sqlens:audit` and `sqlens:doctor` accepted the connection, because they go through the resolver, while `sqlens:drift`, `sqlens:postdeploy`, `sqlens:format` and `sqlens:agent-rules` refused the **same** configuration. ⚠️ **And one of the nine had a side effect**: the runner refuses to open mariadb, sqlite and sqlsrv precisely so that SQLite does not create the file it is pointed at, and a url-configured SQLite fell outside that list — the connection opened, the file appeared, and only then was the driver refused as a non-goal. All nine now go through one call, and a check over the shipped tree keeps the raw key from coming back. The advice text for a connection that really declares no driver names both ways now, not just the key: a url whose scheme names the driver configures one just as much. ⚠️ **This is the second pass at the same class** — the 0.1.0 audit found two of these readers, both were fixed, and the rest of the tree was never swept. The check is what makes a third pass unnecessary.

- **An application that renames its migrations ledger is no longer told the table is missing.** `database.migrations` has two shapes — the name itself, and an array carrying it under `table` — and the two places that build the pending resolver passed the literal `migrations` instead. That was not a default: it **overrode** a decision the application had already made. The consequence is not a silent green, which is what made it easy to miss — `hasTable('migrations')` returns false and the run reports "no migration table". The table exists. The reader goes looking for one that is not missing, and in that application `sqlens:lint` never judges a pending migration and `sqlens:drift` never resolves a pending state, permanently rather than as an edge case. The narrowing now lives in **one** place, which the driver registry — the only reader that had it right — uses as well, and a check over the shipped tree keeps any future caller from naming the table by hand. Both shapes are covered, on both engines, against real servers.

- **"My own time budget" and "the database is in trouble" are told apart correctly on both engines now, by one classifier instead of two wrong ones.** A SQLSTATE alone cannot answer that question. On PostgreSQL the catalog path knew only `57014`, so the reader's own `lock_timeout` — which answers `55P03` — was reported as an unexpected database error with the raw driver message, sending an operator to look for a server fault that does not exist. On MySQL the answer was worse in the other direction: `HY000` was read as "the server was not at fault", and `HY000` is the **general** error class, worn equally by a gone server (2006), a lost connection (2013) and a full disk (1030). Each of those was reported as a bound this package set on itself. `70100` was read as our own timeout too, and it is `ER_QUERY_INTERRUPTED` — somebody else's `KILL QUERY`, the opposite of a bound we chose. All five shapes were **measured** against PostgreSQL 18.0 and MySQL 8.4.10 by provoking each bound rather than taken from the references. The classification now goes through the one classifier the shadow path has always used, and the driver's own error number travels with the SQLSTATE, because on MySQL the SQLSTATE carries no information at all. ⚠️ Two arms that pinned the old behavior are **reversed rather than deleted**, and the detector now reads the driver code off the exception itself as well as off a wrapped one — several catalog readers catch the PDO error directly, and for those it had always answered "no code", which on MySQL means "not a timeout".

- **The PostgreSQL schema-security adapter names the connection it could not reach, not the connection's coordinates.** When `postgrestools` cannot open the database it exits 1 and writes plain text where the JSON report belongs — the ordinary shape of the most likely misconfiguration — and the adapter turned that into a finding whose message spelled out the host, the port and the database name. That message goes through every reporter and leaves the machine. The package masks exactly those values elsewhere, and the stderr excerpt appended to the same sentence is redacted, so the protection reached around precisely the part that needed it. The message now names the **connection**, which is what the reader is holding the configuration for: they find the host under that name, and the report gains nothing by repeating it. ⚠️ A unit test pinned the old text, which means it was an assurance rather than an oversight — it is **reversed rather than deleted**, so the shape stays held and the sign is what changed.

- **The MySQL deploy gate no longer counts a neighbor account's privileges as your own.** `GRANTEE` is rendered `'user'@'host'`, and the grant check matched it with `LIKE "'<role>'@%"`. In `LIKE` an underscore is a **single-character wildcard**, so `'deploy_user'` also matched `'deploy-user'` — and if that neighbor held `ALTER`, the gate read it as held and waved the deploy through. It then dies halfway into `migrate --force`, on the grant error the gate exists to find. A gate that fails **open** is worse than no gate, because it replaces the check somebody would otherwise have made by hand. Measured on MySQL 8.4.10 with exactly that pair of accounts. ⚠️ **The obvious repair is wrong in the other direction and is pinned against:** `substring_index(grantee, '@', 1)` splits at the first `@`, so an email-shaped account — `sqlens@mail.test`, an ordinary thing to call a user — is cut in half, matches nothing, and reads as holding no privileges at all, which this check turns into a false `MISSING_PRIVILEGE` finding. What replaces the `LIKE` is a prefix comparison: no wildcard to escape, no separator to guess at. ⚠️ And one half of the finding did **not** reproduce: a quote in an account name causes no false finding, because `information_schema` renders it **undoubled** (measured on the same server) and the pattern was bound rather than interpolated. The arm stays as a regression guard and says so.

- ⚠️ **The fifth redaction sink was wrong and is not in this release — it was built, shipped to `develop`, and taken back out.** `CheckResult::undetermined()` looked like a safe sink for the same reason the four real ones are: the field explains why something could **not** be read, and a measurement over its forty-three call sites found no identifier in any check's own prose. The measurement searched for `role "…"`. The prose uses **backticks** — `GrantCheck` writes ``the migration connection names the role `deploy` `` — which is one of the three quote styles the redactor handles and the one the scan did not look for. So the sink removed the role name a reader had typed into their own configuration, which is the answer the check exists to give. What the gate caught is worth naming: an arm that pins `names the role on the run it produced, so the withholding is checkable`. The ten deploy checks that compose a driver's message are redacted individually instead, at the seventeen places where the text is a driver's and nothing else, and the factory's docblock carries the reason so the generalization does not look obvious a second time.
- **A driver's error message no longer carries the connection's coordinates into a finding.** Eighteen places wrote `Throwable::getMessage()` into finding and notice text with no redactor at all, and `QueryException::formatMessage()` appends ` (Connection: …, Host: …, Port: …, Database: …, SQL: …)` to **every** query exception on both engines. The leak path is the expected path, not an edge case: a refused catalog read on a managed instance — which the collectors' own comments call the ordinary case — therefore arrived wearing the host, the port and the database name, and went straight into a report. One of the fields involved had a docblock saying in so many words that its text must never be shown as-is because it can carry a host and a database name; it was shown as-is, by two readers, through the audit's notices. The redaction now happens where that text **arrives** — the cross-fact detail, a failed settings reading, an undetermined pooler reading, and a crashed half of a security run — so each covers a whole family of producers and a nineteenth inherits it without knowing it exists. ⚠️ **Deliberately not at `Finding`**, which would be a filter rather than a sink: the shape redactor removes `role "…"`, `user "…"` and `database "…"`, and that is precisely what a **security** finding about a role or a database is made of. These four fields carry error text and nothing else. The diagnosis still travels — `SELECT command denied` survives the redaction, because a report that lost the reason would be a worse one rather than a safer one.

- **A hostname that does not resolve no longer reaches any report, on either engine.** A wrong `DB_HOST` is the most common misconfiguration there is, and it is the one error whose message the redactor could not see: there is no `host=` pair in it, it is not the libpq `connection to server at "…"` preamble, and Laravel's own `Host:` suffix is appended to a **query** exception, which a connect failure never becomes. Every pattern walked straight past the name. Both shapes are now removed, and both were **measured against the real drivers** rather than reconstructed — `could not translate host name "…"` on PostgreSQL, `getaddrinfo for … failed:` on MySQL, the second carrying the name unquoted so the pattern has to stop at `failed` rather than at the first space. ⚠️ There is no server to measure this against and that is the point rather than a gap: a name that does not resolve never reaches one, so the message is the client library's and the shape is the same whatever is running. An ordinary schema error is still untouched — `relation "users" does not exist` passes through whole, because a redaction that ate the diagnosis would trade one unusable report for another.
- **And it is removed for every `--format`, not only for the one that happened to redact.** The two halves of credential redaction were wired to different callers: the value-based pass, which knows the configured password, url and dsn, ran on the `agent` reporter alone; the shape-based pass, which knows what the drivers print, ran at a handful of translation sites. Console, JSON, SARIF and GitHub got whichever one the producer happened to apply. They are now one object, resolved from the container, applied where the notice is built — values first, then shapes, an order that is a correctness property and is stated as one: the shape pass rewrites its matches, so a configured secret sitting inside a recognized shape would be gone before the value pass could learn to recognize it anywhere else in the message.

- **Every catalog function the PostgreSQL driver calls now carries its schema, so no user function can answer for it.** `pg_catalog` is searched implicitly and FIRST, which covers relations — and does not cover functions. Function resolution picks the best candidate among **different** signatures, so a user function taking `text` where the catalog one takes `name`, or matching a type exactly where the catalog one needs a cast, wins. Measured on PostgreSQL 18.0 with a user function in `public`: `array_to_string`, `obj_description` and `array_agg(name)` all resolved to the substitute, and `pg_has_role(current_user, 'no_such_role', 'member')` answered **true for a role that does not exist**. That last one is why this is a security fix and not hygiene — a hijacked privilege check does not crash an audit, it **answers** it, and the report then says green over a forged answer. `SET TRANSACTION READ ONLY` is no defense: the attack needs no write. The precondition is ordinary rather than exotic — any role with `CREATE` on a schema in the audit role's path, which every database created before PostgreSQL 15 and carried forward by `pg_upgrade` still grants to `PUBLIC` on `public`, and which a `"$user"` schema grants by construction. **A pinned `search_path` was tried first and rejected**, because this package deliberately reads the session's own path as data in three places — the default schema scope, `current_schema()` for an unqualified RLS entry, and `pg_table_is_visible()` — and pinning it makes all three answer about `pg_catalog`, which scopes every reading to the system catalog and reports a project's own schemas as empty. Qualification fixes the hole without touching what the session resolves. **Nothing about a reading changes**; the same rows come back, from a catalog that cannot have been substituted.
- **A source guard keeps that true, and it asks the server rather than carrying a list of names.** Of the bare identifiers the query-issuing PostgreSQL surfaces call inside SQL, it asks `pg_proc` which ones PostgreSQL itself resolves in `pg_catalog` — those are exactly the ones a user function can outrank — and requires each to carry the schema. SQL constructs that merely parse like a call (`extract`, `coalesce`, `nullif`, …) and type names used as casts are declared exemptions with their reason, because a schema in front of either is a syntax error rather than a hardening. `Rules/` and `Remediation/` are out of scope on purpose: the SQL there is the user's migration being matched or advice being printed for somebody else to run.

- **Nothing SQLens sets on PostgreSQL outlives its own transaction any more.** The reader bounded its session twice — once as `SET LOCAL` inside the read transaction, once as a plain session `SET` before it — and called the second one "the belt to that brace". Behind PgBouncer in transaction pooling the belt is the damage. A session `SET` there lands on whichever backend carried that one statement and stays on it: `server_reset_query` runs only in session pooling by default, and `track_extra_parameters` can only reset parameters the server announces through `ParameterStatus`, which `statement_timeout`, `lock_timeout` and `idle_in_transaction_session_timeout` are not. The next session of the **host application** handed that backend inherits a five-second statement timeout and an idle-in-transaction timeout it never chose, and starts losing queries to `57014` and transactions to a FATAL `25P03` — and the reader connection is a copy of the application's own configuration, so it goes through the same pooler. Every bound is now `SET LOCAL`, including `idle_in_transaction_session_timeout` and `application_name`, both of which accept it; the transaction is the only scope where the first one has anything to do at all. Nothing is dropped and nothing is weaker: `SET LOCAL` covers a direct connection exactly as well, which is why this is unconditional rather than dependent on a pooler verdict the probe itself admits can read wrong under load. **The pooler probe no longer bounds itself either** — it is the one read in the package that cannot run inside a transaction, because pooling is invisible in one, so its session `SET statement_timeout` was the exact leak it exists to detect, performed by the detector; four constant-time statements now run with whatever bound the connection already carries. **And `sqlens:lint` no longer writes onto a borrowed connection that measures as multiplexed**: before bounding the host's session it asks `pg_backend_pid()` twice, and a changed backend is conclusive evidence of multiplexing that nothing else produces. On that evidence it writes nothing and restores nothing, because a snapshot read on one backend and written back on another is the same leak wearing the word "restore". A stable pid is treated as *no evidence of pooling* rather than proof of a direct connection, so the bound a direct connection has always had is unchanged. ⚠️ **The pooler semantics rest on PgBouncer's documentation, not on a probe**: a confirming lane with a real pooler is CI infrastructure and is tracked separately.

- **The shadow guard, the confirmation prompt, `sqlens:drift` and `sqlens:doctor --probe` now resolve the connection the way every run does.** `sqlens.connection` is an ordinary documented key and it comes FIRST — before `database.default` — for lint, audit, baseline and the agent rules. Four places re-implemented that resolution and read the host default alone, so the moment a project set the key each of them answered about a connection nothing was running against. The worst of the four is the production guard: with `sqlens.connection` pointing at a production database and `database.default` at something harmless, the detector was handed the harmless name, found nothing to refuse, and a mode whose whole purpose is to CREATE and DROP a database was cleared to run against the other one. The detector calls itself the last line and is deliberately generous for exactly that reason; it was being asked about the wrong database, so its generosity never came into play. The confirmation prompt inherited the same name, which means the person typing yes was told about a database the run would not have touched — an informed consent that was not informed about the right thing. `sqlens:drift` compared a different database than `sqlens:lint` linted, and it creates a reference database to do the comparison; `sqlens:doctor --probe` with no value opened a connection nobody asked about, from the command whose entire job is reporting what SQLens sees. All four now ask `DriverManager::defaultConnectionName()` instead of re-deriving the answer, which is the only version of this that cannot drift apart again. **Nothing changes for a project that does not set `sqlens.connection`**, which is why this went unnoticed: the two keys agree until one of them is used.

## [0.19.0] - 2026-09-19

### Added

- **Every answer a predeploy check could not give now carries its reason as a NAME, and the gate's escape hatch takes a list of those names.** The reasons have always been sentences — specific on purpose, because "which view refused" and "which privilege is missing" are what somebody needs in order to act — but a sentence is not something a configuration can hold. So `deploy.predeploy.allow_undetermined` could only ever be one bit: waive everything that could not answer, or waive nothing. That made two very different situations one decision. "The tool that formats a plan is not installed on this runner" is a fact about the runner a project may reasonably deploy past; "the privilege table could not be read" is that same project not knowing whether the deploy is allowed to do what it is about to do. A project that needed the first had to grant the second. The key now also accepts a list — `'allow_undetermined' => ['missing_external_tool']` — and the gate proceeds only when **every** unanswered question on the run is named on it. Partial coverage stays shut: the run is blocked by nothing else, so one uncovered reason is a question the deploy would otherwise proceed past unanswered. `true` and `false` mean exactly what they meant, `--allow-undetermined` still waives whatever could not answer for the run somebody is watching, and all three are recorded the same way in the report's `undetermined_waiver`.
- **The JSON report names it too: an undetermined finding carries `undetermined_reason` beside its sentence**, and the run summary's histogram counts every reason this build knows. Both are additive — nothing that was in the document has moved or changed shape.
- Every name is validated against the reason vocabulary, on both hatches, so a misspelled entry is reported at the index that is wrong rather than quietly narrowing what a project thought it had waived. An unknown name, a value that is not a list, a list naming nothing valid: each closes the hatch rather than opening it.

### Changed

- **The waiver line says what was waived, not only that something was.** A predeploy that proceeds past unanswered questions has always recorded the fact — `undetermined-waiver=on` beside the result, so a green can be told from a waved-through one. With a named list that line was no longer specific enough: a project that decided it can deploy past one reason and a project that opened the hatch for everything printed the same word. It now reads `undetermined-waiver=missing_external_tool` when a project named what it accepts, and still `on` when the decision was the wide one — `--allow-undetermined` and `true` are not a list of every case, and rendering the reasons that happened to come up would claim somebody chose them. What it names is what the run actually raised, not what the config holds: a project may name three reasons and meet one, and saying all three would claim the run waived more than it did. **The JSON envelope is unchanged and `schema_version` stays at 6** — adding a key bumps it for every consumer, and the boolean there already answers the question that document exists to answer.
- **The reason text of an undetermined result now opens with its name, as `reason_name: the sentence`.** Most of these read that way already — the convention was there long before anything enforced it — but nineteen of them did not, and their wording on the console and in the report gains the prefix. The sentence itself is unchanged. It is composed rather than left beside the name so that the token is legible exactly where the failure is read: an operator who wants to allow that answer has to name it, and prose alone would send them to look it up.

### Fixed

- **The bug-report form no longer tells a Laravel 12 user they are unsupported.** Its checkbox asked a reporter to confirm "PHP ^8.4, Laravel ^13" while `composer.json` declares `^12.0 || ^13.0` across every illuminate component. The form ships to the public mirror and is where every bug report starts, so the first thing a reporter on the older major read was that this package excludes them — and it never did. It now names both majors, and a new arm holds the form and the manifest to each other so widening or raising either floor cannot leave the form behind again.

- **The `predeploy` MCP tool now reads the same waiver the command does, so one run cannot get two verdicts.** The escape hatch became a list of reason names in this release, and `sqlens:predeploy` honors it — but the tool over the protocol read only its own boolean parameter and never looked at the configuration at all. A project that had declared `'allow_undetermined' => ['missing_external_tool']` therefore got a clean exit on the command line and a block from the tool, for the same database at the same moment. The tool's own comment says the two "must not be able to disagree about whether a deploy proceeds, and two readings of the same results are two chances to"; this makes that true again. The parameter is unchanged in meaning and still wins in both directions — it is the counterpart of the `--allow-undetermined` flag, a per-run judgment by somebody watching, and all-or-nothing on both sides. What changed is its **absence**: leaving it out used to mean `false`, and now means what the project declared. The answer's `allow_undetermined` field says whether the hatch was open at all, including on a run where nothing went unanswered and it changed nothing; whether it was actually used is `undetermined_waiver` in the run header, which on this path was previously `null` — "this producer has no gate" — on every run. **The envelope is unchanged and `schema_version` stays at 6.** The tool reaches the waiver as a value object the console command also uses, which is the only relationship the agent layer has to the engine — it gained no path into the console layer, and the architecture guard that holds that line names the new door with its reason.

## [0.18.0] - 2026-09-17

### Added

- **A unique index over `lower(column)` is now reported as the guarantee it is: `PG.L8.UNIQUE_CASE_FOLDED`.** `CREATE UNIQUE INDEX users_email_lower_unique ON users ((lower(email)))` promises that no two rows hold addresses equal once case is folded away — and nothing about the column says so. The column is still `email`, the model still says `unique:users,email`, and an ordinary `where('email', $input)` compares something the index does not constrain. For an address stored as `Taken@Example.com` a check for `taken@example.com` finds nothing, the code concludes the address is free, and the index then refuses the write: the caller was told two different things by two parts of one system. On an endpoint deliberately built not to reveal whether an account exists, the difference between "not found" and "refused" is the disclosure, and that is the case this rule was built from — found by hand in a real application, because no run could say anything about the index. **The remedy is never to drop it.** Fold on the way in so the stored value is the comparison key, or make every lookup fold the way the index does; the rule's page states both and says which one a job or a second application argues for. It sits at level 8 with the other convention rules rather than at level 6, because levels are cumulative and a lower one reaches more consumers: this is a statement about a deliberate structural decision, not a defect, and it belongs to the band a project turns on when it wants to hear about those. It is deliberately not a `security` entry for the same reason — security and privacy bypass the level gate, and an entry there that names an intact schema is how a security finding stops meaning something is broken. **Silence is not an all-clear**: a `citext` column or a case-insensitive collation makes the same promise with no expression to recognize, and this rule cannot see either.
- **The reading behind it takes the spelling the server produces, which is not the one the migration wrote.** `pg_get_indexdef()` prints a key position from the parsed tree: the doubled parentheses a portable migration needs for MySQL are gone, and a cast has appeared wherever the column is not `text` — `lower(email)` over a `varchar` column arrives as `lower(email::text)`. Laravel's `string()` column is `varchar`, so the cast form is the ordinary one and a check written against the bare spelling would match nothing at all while looking entirely correct. A fold wrapped in anything else is refused rather than approximated: `lower(btrim(email))` is unique over a value that is folded *and* trimmed, and a sentence about the column's case would be false about it.

## [0.15.0] - 2026-09-15

### Added

- **A catalog finding can point at the migration that introduced its subject.** A lint finding knows its file and line because it reads migrations; an audit finding reads a DATABASE, and the database has never heard of `2024_01_11_000000_create_orders_table.php` — it knows `public.orders.customer_id`. So an audit finding landed in a log while the person reading the pull request was looking at the migration diff, and a finding in a log is one somebody has to go looking for. The anchor is resolved by reading `database/migrations` the way the rest of the package reads migrations — parsed once, never included, no connection and no migrator — and a finding that gets one now carries the file and the line of the call that created the table or the column.

  **Both output paths carry it.** `--format=github` puts the annotation on the migration's own line, so it lands in the diff of the pull request rather than in a log; SARIF uses the migration as the alert's physical location, with its real line. What does not change is the subject: the object stays in `logicalLocations`, the physical location is still flagged `sqlens-anchored`, and a new `sqlens-anchor-kind` distinguishes a real migration from the configured stand-in used when there is none. A migration is where an object came FROM — the finding is about the object as the database holds it now, and a `CREATE TABLE` that was correct on the day it ran is the ordinary case. Both reporters say that in the message rather than leaving a reader to infer it from a file name.

  **Every failure is an ABSENT anchor, never a wrong one.** A table named by a variable or a constant, a file that will not parse, a project that has run `schema:dump --prune` and has no migrations left to read: all of them answer nothing, and the finding is reported exactly as it was before, without a file and a line. That asymmetry is deliberate — a missing anchor costs a reader one search, and a wrong one sends them to edit a file that had nothing to do with the finding. It is the same reason the scan will not resolve `self::TABLE` by reading the class: it could, and each place it would have to look is one more place to be confidently wrong.

  **It is presentation, and that boundary is held rather than promised.** The anchor never changes a severity, a downtime class or whether a finding stops a build, and it never enters a fingerprint — a renamed or moved migration must not invalidate a baseline entry, because the database that entry describes did not change when somebody moved a file. Two smaller decisions are worth naming: the first writer wins, so a table created once and altered three times anchors to its creation rather than to its last edit; and the table a column belongs to is tracked by nesting rather than by the receiver's name, so a migration that calls the builder `$t` is read like every other one. The resolved path is `database/migrations` alone, which is a deliberate floor — the full set needs the application's migrator, and a rule that reached for the container would stop being answerable from a bare project root. A package that registers its own migration path simply yields no anchor, reported the same ordinary way as a squashed schema.

- **A narrowing foreign key carries fix material, not just a sentence.** `PG.L9.TYPE_IMPLICIT_CAST` reports a key whose two ends are different types, and for the one shape with a dated failure — a single-column key whose referencing side is a narrower integer than the key it points at — the only suggestion it gave was prose in the message. It now carries a machine-readable payload, so the agent reporter, the GitHub reporter and `capture` all have something to hand on. The sequence is expand/contract, every step its own migration: a wider column beside the old one, a backfilled job, a release writing both, the constraint moved, the old column dropped last. `ALTER TABLE … ALTER COLUMN … TYPE bigint` reaches the same end state in one statement and is named in a precondition rather than emitted — on PostgreSQL it rewrites every row under `ACCESS EXCLUSIVE`, blocking readers as well as writers, and the size at which that stops being acceptable is a fact about your table. The other shapes reach a considered `none` rather than silence: a composite key, whose columns cannot be widened one at a time without deciding an order; a pair where the referenced key is the narrower side, where matching them means moving the parent; and a pair that is not two widths of one number, where the right answer depends on which side is telling the truth about the data. The MySQL rule offers no material and its page says why: the server refuses the narrowing integer pair outright when the key is created, so that shape never reaches a MySQL catalog. A pair whose verdict is UNDETERMINED carries nothing: a table whose only mismatched key has an end the catalog could not read is reported as undecided, and material beside that would read as advice about the thing the rule just declined to judge.

- **A table somebody switched autovacuum off for is reported: `PG.L7.AUTOVACUUM_DISABLED`.** `ALTER TABLE … SET (autovacuum_enabled = false)` is sometimes the right call — a table bulk-loaded on a schedule is vacuumed better at a chosen moment than at an arbitrary one — and what makes it worth a finding is that the decision outlives the reason and nothing else in the database mentions it again. Two consequences, and the second is the one that surprises: dead rows are not reclaimed, so the table's file size stops saying anything about the rows a rewrite would copy and its row estimate goes stale with it (autovacuum is what triggers most `ANALYZE` runs); and the setting **does not avoid the vacuum**, it defers it — when the table crosses `autovacuum_freeze_max_age` the server starts an anti-wraparound vacuum on it regardless, that worker does not yield to a lock request, and by then there is more to do. `DEPLOY.PREFLIGHT.FREEZE_HORIZON` is the deploy-time half of the same fact.

  Three states are read out of `pg_class.reloptions` and only one is reported: `false` is the finding, `true` is somebody being deliberate the other way, and **absent** — the ordinary case — means the table runs under the cluster's setting. The value is kept as the server's own spelling rather than cast to a boolean, because a boolean has no third value and the third value is the common one. A hand-maintained table is a real false positive and the finding says so: this check cannot see the cron that vacuums it, so the answer is an `ignore` entry with the reason beside it rather than a heuristic guessing at intent from a name or a size. PostgreSQL only — InnoDB has no per-table equivalent, and `STATS_AUTO_RECALC` decides whether optimizer statistics are refreshed, not whether dead rows are reclaimed.

- **The deploy report names an autovacuum-off table it is about to touch: `DEPLOY.PREFLIGHT.AUTOVACUUM_DISABLED`.** The audit rule above reports every such table in the database, which is the right shape for an audit and the wrong one for a deploy — the list is read once, and somebody planning a migration has no reason to go back to it. This check asks the narrower question at the moment it matters, and it adds a consequence an audit cannot state: **the run's own estimates for that table are the least trustworthy figures in the report.** A table without autovacuum keeps its dead rows, so its file size stops predicting what a rewrite would copy and its row estimate goes stale with it, and every duration and size stated here for it is derived from exactly those two numbers. The second consequence is the one `DEPLOY.PREFLIGHT.FREEZE_HORIZON` measures from the other end: the setting defers the vacuum rather than avoiding it, and the anti-wraparound worker that eventually arrives does not yield to a lock request.

  It looks at **every** table the pending statements name as their subject, whatever they do to it — deliberately wider than the lock-shaped checks beside it, because a stale estimate spoils the numbers for any statement whose cost the report estimates, not only for one taking an exclusive lock. A table a statement merely refers to is left alone. It reports at a fixed `medium`: it does not stop a deploy, so reporting it beside a finding that does would teach a reader to discount both, but it changes what every other number for that table is worth. A hand-maintained table is exempted with an `ignore` entry and its reason — the cron is not in the catalog, and a heuristic guessing at intent would silence the common case to spare the rare one. PostgreSQL only.

- **A migration's column definitions reach the rule layer, so a lint rule can ask what a column IS.** They never did: `keyColumns` carries an index's key, not a type, and the body a `CREATE TABLE` writes was not looked at. Every rule whose judgment needs a column type was therefore **structurally audit-only** — not because that was the right answer, but because the question could not be put. The catalog answers it once the table already stands; the migration that introduces a wrong type is the cheapest moment to fix it. Both grammars are read: the parenthesized body of a `CREATE TABLE`, and the trailing type of an `ALTER TABLE … ADD COLUMN` — including MySQL's bare `ADD` form, which is the one Laravel actually emits.

  **The type goes through the same normalizer the catalog reader uses**, and that is the part that makes the two comparable rather than merely similar: `CanonicalType::fromRaw()` already speaks both vocabularies, so a migration's `bigserial` and the catalog's `bigint` land on one name, as do `varchar` and `character varying`. There is no mapping table in this layer and there must never be one — two normalizers would be two answers, and a lint verdict and an audit verdict about one column have to be the same verdict.

  **All or nothing, and null rather than empty.** A member whose shape the reader does not recognize declines the *whole* body: a rule handed nine columns out of ten cannot tell one is missing, and the finding it then makes is wrong in the silent direction and permanent. An empty list is never produced, because a table with no columns is not a thing — so null means "nobody read one here", which a rule turns into silence or `undetermined`. The same distinction runs one level down: a column whose type could not be read arrives **present** with a null type, because "this column is absent" and "I could not read its type" are different answers.

  One discriminator is worth naming because an arm found it rather than review: **a column name is quoted** after identifier normalization, and a bare word opening a member is not one. `CREATE TABLE clone (LIKE users INCLUDING ALL)` is a real body member that brings columns this reader cannot see, and `LIKE` is in neither driver's keyword list — so without the test it arrived as a column *named* `like`, typed `users including all`. Adding `LIKE` to the keyword lists would fix it and cost a canonical form-version bump, which moves every fingerprint and baseline entry in every project. A user-defined type is unaffected: there the name is quoted and only the type is bare. The keywords that end a type belong to the **driver**, because `CHARACTER VARYING` is a type on PostgreSQL while `CHARACTER SET` is a modifier on MySQL.

- **A `lock_timeout` that is not smaller than `statement_timeout` is reported: `PG.L3.LOCK_TIMEOUT_INEFFECTIVE`.** The two clocks bound different things and one of them is nested inside the other — `lock_timeout` the wait in the lock QUEUE, `statement_timeout` the whole statement including that wait. Set the second to a number the first cannot reach, and equal is already too large, and the statement is aborted before the lock wait ever gets to its own limit: the lock clock is configured, visible and dead. The configuration reads like a safety net because both values are set and both are non-zero, and **the failure afterwards is mislabeled as well** — the statement comes back as a *statement* timeout, so whoever reads the log concludes the DDL is slow and goes looking at the table, when the migration never got the lock at all. Two diagnoses, opposite ends of the problem. This package recommends both clocks in its own remediation preamble and justifies them by exactly this difference, so an arm proves the shipped template can never produce such a pair: every step it emits carries a placeholder rather than a value, so there is no pair of numbers in it to be wrong.

  **It judges `reset_val`, not `setting`, and getting that wrong would have made the rule judge SQLens.** This audit sets both of these timeouts on its own session before it reads anything, so the session value describes the tool on every server it is ever pointed at. `reset_val` is what the configuration file, the database and the role have settled between them — the pair a fresh deploy session inherits before it sets anything itself. Which layer named either clock is measured beside it from `pg_db_role_setting`, because `pg_settings.source` answers about the reading session and a reader told the pair is wrong still has to choose between `ALTER DATABASE`, `ALTER ROLE` and `postgresql.conf`; neither clock appearing there is a measured answer and says the pair came from the file or the default. Two states are deliberately not reported: `lock_timeout = 0` is unbounded rather than ineffective and is already `PG.L3.MISSING_LOCK_TIMEOUT`'s finding, and `statement_timeout = 0` means there is no statement clock to abort first. MySQL gets no twin — `max_execution_time` applies to read-only `SELECT`s so it cannot abort this DDL, and `lock_wait_timeout` and `innodb_lock_wait_timeout` are separate clocks with separate reach rather than one nested in the other.

By maturity: **232 stable**, 3 preview, 2 experimental. **157** answer to the level gate; the other **80** carry a severity — 7 critical, 32 high, **29 medium**, 8 low and 4 info. None of the three carries a `downtime_class` — nothing here is a schema change, the preflight check reports on the trustworthiness of an estimate rather than on an operation, and the timeout pairing is a statement about configuration — so that count stays at 58 entries.

## [0.14.0] - 2026-09-14

### Changed

- **A PostgreSQL row estimate now says how far the table has drifted since the statistics were taken, not only when they were taken.** The age alone cannot tell a reader whether a number still holds: a statistic from a year ago on a table nobody has written to is exactly right, and one from an hour ago on a table that doubled since is out by a factor of two — and both render identically as a timestamp. The statistics reader picks up `pg_stat_all_tables.n_mod_since_analyze` on the join it was already making, and the console narration reports it as a ratio of the estimate (`1.5x` means half again as many rows changed as the estimate claims the table holds). It is not clamped, because a table that turned over three times is the case that matters most; an estimate of zero rows reports no ratio rather than dividing by nothing. **Silence means not counted, never "nothing changed"** — every size estimate is in that state, and so is every MySQL reading, because InnoDB keeps no counterpart figure and its `last_update` answers the question the age already answers. The drift is advisory prose and deliberately does **not** appear in the JSON report or in the stable rendering a determinism digest is taken over: a new key in either would be a schema change and a new digest for every unchanged database.

- **A server setting whose change is waiting for a restart is no longer reported as fine.** PostgreSQL's `pending_restart` says somebody already changed a value, the server accepted the change, and it applies at the next restart — so from that moment the running value and the decided value are two different things, and only the running one is in the catalog. Every server-baseline rule read that flag through the subject and none of them asked about it. A setting that is correct **right now** and carries a pending change is now `undetermined` with the new reason `setting_change_pending_restart` rather than a silent pass: a green that expires at the next minor upgrade or failover is a green nobody scheduled. A value that is **already wrong** is still reported as wrong, with the pending change added to the finding rather than replacing it — the problem is present-tense either way, and a reader fixing the running value needs to know the configuration file already says something else. The run names the running value and says why it cannot name the other one: the decided value lives in the file, not in `pg_settings`. **MySQL is untouched** — it has no counterpart, and the reader reports `null` there rather than `false`, so only an explicit `true` produces any of this.

  **Upgrade:** `setting_change_pending_restart` is a new value in the undetermined reasons of the JSON report. Under `strict_undetermined` — which `--profile=ci` sets — a server with a pending change now moves the exit code where it previously did not. That is the finding doing its job; suppress it per variable through `ignore` if the change is deliberate and waiting for a maintenance window.

### Added

- **A polymorphic column pair with no index over it is reported: `PG.L5.MORPHS_NO_INDEX` and `MY.L5.MORPHS_NO_INDEX`.** A polymorphic relation resolves by BOTH columns at once — `commentable_id = 7` names a post, an invoice and a user, and only `commentable_type` says which — so every access through the relation constrains the pair. Without an index over it each of those reads the whole table, and the cost grows with the table rather than with the number of relations. Nothing in the schema hints at it: a foreign key at least announces the relationship it belongs to, while a polymorphic pair is two ordinary columns whose meaning lives in the application. `morphs()` writes the index along with the columns; hand-written columns and a `nullableMorphs()` that a later migration replaced with its two parts regularly do not.

  The **order** is part of the finding. A B-tree serves a left prefix, so an index leading with the type column answers both the paired lookup and a type-only one, and one leading with the id answers the pair and an id-only lookup nothing performs. An index the wrong way round is therefore reported as its own sentence — *replace this index* rather than *add one*. Told merely that no index exists, a reader adds a second index over the same two columns, and `PG.L7.INDEX_REDUNDANT` then reports that.

  Both rules are **audit-only, and structurally so**: the judgment needs the type of both columns, and a `CREATE TABLE` statement carries none. The pair is identified by naming, so a `<prefix>_type`/`<prefix>_id` pair that merely happens to be named that way is a false positive by construction and belongs on the ignore list — the catalog can prove the columns exist and what they hold, never that `morphs()` wrote them. The id side deliberately does not accept `varchar` or `text`, which Laravel never writes for a morph id, and does accept the `char(36)` and `char(26)` that `uuidMorphs()` and `ulidMorphs()` write.

  Unlike the foreign-key rule, this one exists on **both** engines. `PG.L5.FK_NO_INDEX` has no MySQL twin because InnoDB creates that index itself; measured against 8.4, it does nothing of the kind here, because a polymorphic pair is not a declared relationship and the server has never been told the two columns belong together.

- **A deploy is warned when a table it locks is near its freeze horizon: `DEPLOY.PREFLIGHT.FREEZE_HORIZON`.** An ordinary autovacuum yields to a conflicting lock request and the `ALTER TABLE` behind it proceeds. One running to prevent wraparound does not: it holds its lock to the end, because the alternative is a cluster that stops accepting writes. On a large table that is hours, and from outside it does not look like a lock at all — `pg_locks` shows your statement waiting, the holder is a background worker, and the deploy simply does not move.

  The check reads **both** freeze clocks for the tables the pending run will lock, and holds them against the thresholds the **server** carries rather than hard-coded numbers. The second clock is the one nobody watches: multixacts are consumed by **locking**, not by writing — one is created as soon as a second transaction locks a row somebody else already holds, which is the ordinary state of a foreign-key check — so a lock-heavy table can be spotless on the transaction clock and be the table that stops the cluster. A worker already running is named with its phase and block progress from `pg_stat_progress_vacuum`, and the finding says explicitly **not** to cancel it: the launcher starts it again within `autovacuum_naptime`, the work done is thrown away, and the horizon is closer than before. A run that also rewrites a table is told that this makes the window longer rather than shorter. Where the views are withheld — the normal case on a managed instance — the answer is `undetermined` with `freeze_horizon_unreadable`, never silence. PostgreSQL only: InnoDB has no visible freeze horizon.

By category: **141 safety**, 58 security, 17 idiom, **9 performance**, 6 convention and 3 privacy. By maturity: **229 stable**, 3 preview, 2 experimental. **155** answer to the level gate; the other **79** carry a severity, unchanged at 7 critical, 32 high, 28 medium, 8 low and 4 info. None of the three carries a `downtime_class` in the catalog, so that count stays at 58 entries.

The SQLFluff backend upper-cases keywords with the same tokenizer and gets the same fix. Proved three ways: an oracle over the format corpus in three styles (same token sequence, idempotent), the shapes run on PostgreSQL 18.4 and MySQL 8.4 before and after formatting with identical rows, and each lexer rule pinned on its own.

Measured with a `.pg_format` in the working directory: `function-case=2` turned `count(id)` into `COUNT(id)`, `anonymize=1` replaced `'open'` with a random string, and `nocomment=1` removed the comment, all written back into the file. The backend now passes `--no-rcfile`. It also passes `--redundant-parenthesis`, because by default pg_format drops parentheses it considers redundant in DML (`where ((b = 1))` became `WHERE (b = 1)`) and a formatter here rewrites no expression. Measured on pg_format 5.11.

On MySQL those words now keep the case they were written in; a reserved keyword is still upper-cased, and PostgreSQL, which folds unquoted names, is unchanged. The list was read off `information_schema.KEYWORDS` on MySQL 8.4.10, and the MySQL lane holds it against the server it runs on. The built-in core and the SQLFluff backend share the rule.

- **The built-in formatter keeps a two-word clause on one line.** Every clause keyword broke a line on its own, so `INNER JOIN` came out as `INNER` over `JOIN`, `DELETE FROM t` as `DELETE` over `FROM t`, a foreign key's `ON DELETE CASCADE` as `ON` over `DELETE CASCADE`, and the same for `LEFT OUTER JOIN`, `NATURAL JOIN`, `CROSS JOIN`, `ON UPDATE`, an upsert's `DO UPDATE`, `FOR UPDATE` and `COMMENT ON`. The statements were valid; the layout promised one clause per line. `OUTER`, `FOR` and `NATURAL` are now upper-cased keywords, and `NATURAL` starts its clause.

- **SQLFluff no longer refuses a valid statement over one line it cannot shorten.** When `sqlfluff format` finds a line it cannot break below `line_width`, it exits 1 with "Unfixable violations detected." and still prints the statement it formatted. The backend reported that as `format_tool_refused`, so a `CREATE FUNCTION` header longer than the width stayed undetermined and kept `--check` red for good. That exit is now taken as formatted, and the output still goes through the check that it reads as the same statement. A parse error, which exits 1 as well, is still a refusal. Measured on SQLFluff 4.3.0; `sqlfluff lint` names the rule, LT05.

- **The SQLFluff format backend formats.** It passed `--indent-unit` and `--indented-joins`, two flags `sqlfluff format` does not have, so every call ended with exit 2 and every file came back `format_tool_refused`. The backend now calls `sqlfluff format - --dialect … --nocolor` and carries `indent` and `line_width` as in-file directives after the statement, where a project's own `.sqlfluff` cannot override them and a parse error keeps its line number. `sqlfluff format` never changes keyword case, so `uppercase_keywords` is applied by the same tokenizer the built-in core uses. Measured on SQLFluff 4.3.0 for PostgreSQL and MySQL, with `indent: 2` and `line_width: 40`.

- **`PG.L2.CONSTRAINT_NOT_VALIDATED` no longer reports a constraint on a table the same migration just created.** `Schema::create()` with `foreignId()->constrained()` emits the create and then an `ALTER TABLE … ADD CONSTRAINT`, which made every new related table red from level 2 up — and the remediation bought nothing there. The only thing `NOT VALID` skips is the scan of rows already in the altered table, and a table two statements old has none; the locks, including the one on a live referenced table, are taken and released identically either way. A consumer read it back to us after seeing the index rule stay silent on the very same migration.

  **The exception is scoped to what it can justify.** A table the migration *fills* before constraining it — create, backfill, constrain — is still flagged, because there the scan is real and the referenced table waits for it. So is a table created from a query (`CREATE TABLE … AS SELECT`), which is born with rows. The predicate reads the classified targets rather than the SQL text, and it distinguishes the altered table from the merely referenced one by role rather than position.

- **The narrow-primary-key rules no longer report Laravel's own migrations ledger.** `PG.L6.PK_NOT_BIGINT` and `MY.L6.PK_NOT_BIGINT` flagged the `migrations` table in every Laravel application, and no application could act on it: the framework creates that table from `DatabaseMigrationRepository` with `increments('id')`, on every `migrate:install` and regardless of what the application would prefer. Taking the advice would mean writing against the framework's own default on a table the application does not own — so the finding stood in every report and was resolvable in none of them.

  The exemption follows the setting rather than the word: the name comes from `database.migrations.table`, so an application that renamed its ledger has an ordinary table called `migrations`, and an ordinary table is judged like any other. It is the only table either rule treats this way.

  The same findings also read "has **a** integer primary key". The article now follows the type's own first letter, on both engines.

### Added

- **`#[RawSql]` takes a second reason, `interpolation:`, for the case where the rule's own remedy does not exist.** `SEC.INJ.RAW_INTERPOLATION` answers an interpolated value with *pass it as a binding instead*, and for an IDENTIFIER there is no such thing: no engine binds a table, a schema, a partition or a constraint name, in DML or in DDL. A call site in that position could not answer the rule at all — what a project had was a PHPStan `ignoreErrors` entry, which carries no reason, so nobody later knows whether the line was considered, and is scoped by PATH, so the next interpolation in that file, one that DOES have a binding available, is silenced with it. Reported from a consuming project with seventy such call sites. The separation from `reason:` is the design rather than a detail: `reason:` answers why raw SQL was chosen and says nothing about a runtime value inside it, so letting it clear this finding would switch the injection rule off wherever the policy annotation is on — which is most annotated code, since that annotation exists to satisfy the rule beside this one. The two are independent in the other direction too: a `reason:` the run's policy refuses leaves an `interpolation:` standing, because they answer different questions. It reaches a class, a method, a function, a closure and an arrow function, with the same span rule the policy answer has. This package now answers its own rule the same way — nine call sites carry it, and the six-file exemption they used to need is gone. The bundled Boost skill documents it, including the half a reader needs most: where a binding does exist, bind it, because `reason:` alone deliberately leaves the interpolation finding standing.

### Fixed

- **A migration using `->change()` is judged, where it used to be read and then skipped.** Laravel's PostgreSQL grammar appends `comment on column … is NULL` to EVERY `->change()`, comment or not, and that statement form was not recognized — so one column change made the whole migration report `CAP.L0.UNDETERMINED_CAPTURE`, and nothing in it was checked. Measured in a consuming project over 56 migrations: three used `->change()`, three were reported uncanonicalizable, and the intersection was three of three. `->change()` is the Laravel spelling for the column rewrites and NOT NULL sets the lock-hygiene rules exist for, so the blind spot was the shape those rules are for, while the harmless `create` migrations beside it were judged cleanly. Recognizing the statement exposed a second half: `->change()` compiles to a COMPOUND alter, because the builder restates every modifier it was not told to keep, and `PG.L2.TYPE_CHANGE_REWRITE` handed that whole tail to its type matrix — so a bigint widening came back "cannot classify from the migration alone" rather than failing. The target type is read on its own now, and the cut is parenthesis-aware, so `numeric(10, 2)` no longer truncates to something the matrix cannot match. A `->change()` that rewrites the table fails; one whose retyping is free stays silent and still reports the `SET NOT NULL` the builder added on its own; a parameterized `varchar(255)`, which the target alone cannot settle, is still honestly undetermined.

- **A GIN index carrying a non-default operator class names the method as the reason it was not compared, not the class.** `AUDIT.CATALOG.UNREAD.NOT_UNDERSTOOD` reported `non-default operator class: jsonb_path_ops`, which points a reader at the operator class as the thing to fix. Measured against PostgreSQL's own `pg_opclass`: `jsonb_path_ops` is defined for `gin` and for no other access method, so an index carrying it is a GIN index by construction — and a redundancy question is only meaningful inside one method. Teaching the reader that class name would have rewritten the sentence and left the index exactly as incomparable, which is what a consumer proposed after reading the old message. The class is still named where it decides: a b-tree carrying `text_pattern_ops` serves `LIKE 'foo%'` where the default class does not, and those are two different indexes.

- **A published `config/sqlens.php` that sets one nested key keeps every sibling the package ships.** The merge asked one question per TOP-LEVEL key, so answering `security.runtime_connection` froze the whole `security` block: `security.rls.mode` resolved to `null` although the package ships a default for it, and any key a later release adds under `security` would never have arrived. With a reference configuration of about 99 KB the only safe alternative was publishing all of it and diffing after every upgrade. A minimal file — the keys you are answering, nested as they are shipped — is the recommended shape now. Not through Laravel's `replaceConfigRecursivelyFrom()` either, and that is the half worth stating: it is `array_replace_recursive`, which replaces **lists by index**, so `['database/schema/*']` overridden with `[]` stays `['database/schema/*']` and `['a','b','c']` overridden with `['x']` becomes `['x','b','c']` — emptying a list would do nothing and shortening one would keep the package's tail, while `format.exclude` ships with an entry this package's own comments tell a project to empty. The rule instead: where the **package** ships a map, recurse; where it ships anything else, the published value wins whole, empty list included.

- **`#[RawSql]` now works where PHP allows it: on a function, a closure and an arrow function.** The attribute has declared `TARGET_FUNCTION` since it was written, so PHP accepted the annotation without a word — and nothing read it, because the collector visited class nodes only and a call site outside a class reports no scope name to join on. A free function is the ordinary shape for a test harness, and a **file-scope closure is every Pest test body**, which made the duty there not merely hard to discharge but impossible: the only remaining answer was an `exclude_paths` entry over the whole test tree, which silences far more than the finding. Those shapes are joined by POSITION now — everything inside the annotated function-like is covered, including a call one closure deeper, the same reach a method-level annotation has over its own body. The mode is read before the scope now, and the reading carries a third state: the rule answers with `not_applicable` saying this database separates nothing, and names what to change if that stops being true. It also unblocks a pipeline — `undetermined` escalates under `strict_undetermined`, which `--profile=ci` sets, so a project whose tenant separation lives in the query layer previously had to waive every undetermined at once to get a green run.

- **An unqualified name in `security.rls.tables` reaches the table it names.** The list matched only against `schema.table`, so a project that wrote `api_keys` — the name its own migration created the table under — got `not found in the catalog` for every entry: fifteen skips over fifteen tables that exist. The expensive half is quieter than the noisy one, because a security list matching nothing reports nothing and therefore looks configured. A bare name now resolves through `current_schema()`, which is where an unqualified `CREATE TABLE` puts a table rather than a guess about naming; a qualified one behaves as before. And the two ways of failing read differently: a bare name that resolves to nothing says so and suggests the qualified spelling, instead of describing a table that is missing.

Measured in a consuming project: 56 migrations in the directory, 0 read, exit 0. The summary did say `over 0 migrations`, but the exit code — the half an automation reads — said what a run over all 56 would have said. Such a run now carries `LINT.NO_MIGRATIONS_READ`, a named undetermined derived from the COUNT of judged migrations rather than from a list of causes, so a cause nobody has enumerated reports as well. It joins the shipped registry as a safety entry — 136 of them — answering to the level gate rather than to a severity of its own. Under `strict_undetermined` — which `--profile=ci` sets — it moves the exit code; without it the run reports the finding and still exits clean, because a local run after `migrate` should not fail. The `--path` help on `sqlens:lint` and `sqlens:baseline` now says which set it reads, which it only implied.

- **`sqlens:lint --file=` no longer dies on a migration written in the old class shape.** Laravel accepts two shapes and the loader read one: a file that RETURNS an anonymous class. A file that DECLARES a named class returns nothing, `require` answers `1`, and the run ended with `resolve(): Return value must be of type Migration, int returned` — accurate, and about a private method of this package rather than the file it concerned. One such file in a project is enough to make the command unusable, and it need not be old code: `vendor:publish` wrote that shape for years, so a published migration nobody has touched since carries it. The fix needs no new derivation — once the file has been required the class IS declared, so the same reflection-checked lookup that came up empty a moment earlier now finds it. A file that is neither shape, such as a class whose name no longer matches the file it lives in, is refused by `UnloadableMigration`, which names the file and what it handed back.

Load two of them into one registry and you keep whichever arrived last, so a `schema_version: 3` payload could be validated against v2, whose `strategy` enum is closed and has never heard of `reindex_before_refresh`. Nothing about validation changes: the documents differed in what they constrain and were identical only in what they called themselves, so every payload accepted before is accepted now. The URLs those identifiers use do not resolve to a page, which is allowed — a `$id` is a name, not a link — and they are unique names again.

Version 2 stays in the package unchanged, beside version 1. The completeness gate counts catalog rules like everything else now, and the named exclusion that said they were structurally out of reach is gone rather than merely empty.

- Fix material for a state finding now reads like one. The renderer says "in a new migration" where a statement's template says "in a later migration" — the second quietly implies an earlier one, and for a finding that came from reading your database there is none. It takes the distinction from the payload's `subject`, never from a shape it recognizes, so there is one answer to that question rather than two that can drift. A state finding's verification line also names the right command: `sqlens:audit` confirms the state afterwards, while `sqlens:lint` judges the migration before it runs — two commands, two moments.

- The extension API is enumerated and diffable. The public-api page has always promised "the interfaces a third-party rule package implements" without ever naming them, so a signature change on one reached you with nothing red in between — the snapshot compared rules, exit codes and schema versions, never a method. All nine are now named in `ApiSurface::EXTENSION_CONTRACTS`, the published snapshot carries each one's method signatures, and the breaking-change check forbids a move in either direction: an interface has no benign one, because adding a method breaks every implementer and removing one breaks every caller. The declared list is held to what rules actually implement by a derived arm, so a new capability interface cannot ship unpromised and a promise cannot outlive the thing it describes. `ProvidesSchemaObjectRemediation` ships `preview`, like the payload it produces.

## [0.4.0] - 2026-09-05

### Added

- `sqlens:format` gains `--format=console|json|github` and positional path arguments. `json` and `github` go to STDOUT, so `--format=json > report.json` yields a file holding nothing but the document, while the console verdict and every degradation notice stay on STDERR. An unknown value is a misconfiguration and is refused before a single file is rewritten, never a quiet fall back to `console`. The JSON document lists every scanned file — including the unchanged ones, which the console deliberately omits — with the run parameters at fixed keys, and the GitHub annotations weigh by the exit code rather than by the wording: an unformatted file is an error under `--check` and a notice in a write run. Past GitHub's ten-per-level cap the run says how many it withheld and which, because a truncated list that does not say so reads like a shorter one.

- `sqlens.format` gains the discovery keys `paths`, `exclude` and `extensions`, which decide which files a run may find. Roots default to the application's migration paths exactly as before, so a project that configures nothing behaves unchanged; the command line still wins over a configured root. `exclude` takes globs and defaults to `['database/schema/*']`, because `schema:dump` rewrites those files from the database anyway — a project that hand-maintains its schema file empties the list, and the run then names the dump files it touched, so the decision is visible in the output rather than only in a config file. `extensions` widens the set to other files that hold nothing but SQL. `php` and `phtml` are reserved and cannot be added: a Laravel migration is a PHP file, and reading one as SQL rewrites the whole file as a single statement, so the value is refused by the config validator and dropped again at runtime. `vendor/`, `node_modules/` and `storage/` are never walked into, symlinks are not followed, and the order is byte-wise so it does not move with the ambient collation.

- Every entry in the shipped rule registry now declares an `attribution`: `authored` when the finding names something you wrote and can rewrite, `observed` when it names what the run found in the world — an unreachable server, a lock another session holds, an index whose build died. It is what decides whether an entry owes a bad/good example pair, and the classification means something in both directions: an authored entry without a pair cannot ship, and neither can an observed one that carries a pair for a migration nothing causes. 159 of the 225 entries are authored, 66 observed.

- `explain_rule` now answers with the ten capture examples, which live on their producers rather than in the bundled register. It read the register alone and reported `registered: false` over examples that exist and are good — including every pre-scan finding, where the example is exactly what turns the rule id into something an agent can act on.

- Two deploy checks gained example pairs: `DEPLOY.LEGACY.CONSTRAINT_NOT_VALIDATED` and `DEPLOY.LEGACY.CONSTRAINT_NOT_ENFORCED`. They are the only two in that family that a migration causes and a migration avoids — the other twenty-two describe the environment the run found, and a pair for one of those would be confident, concrete, and about something else.

- The remediation payload gains a `subject` discriminator: `statement` for a template that rewrites a statement you wrote, `schema_object` for one describing a migration that does not exist yet. It is emitted on every payload, including the default, so you read the shape from the document instead of inferring it from which rule produced the finding. A `schema_object` payload must not carry a `downtime_class` — there is no deploy whose effect it could describe, and one that carries it is refused rather than rendered.

### Changed

- **The remediation payload is now schema version 2, and version 1 is frozen where it was.** `subject` is the only field that moved, but it moved in a way version 1 cannot absorb: the version-1 document is strict, so a consumer holding the copy that shipped with 0.1.2 through 0.3.0 rejects a payload carrying the new key, and requiring the key means the version-1 document in this package rejects a payload written before it. Both would have claimed to be version 1 — the one state the field exists to prevent. Read `schema_version` and treat a number you do not know as a payload you cannot use; that rule was already the documented one and is what makes this a bump rather than a break. `resources/data/schemas/remediation-payload-v1.schema.json` stays in the package unchanged, so an archived payload can still be validated against the contract it was written under, and every version-1 payload is a `statement`. `remediation_schema_version` in the API surface moves with it, which the breaking-change gate already classifies as allowed in a minor while the payload is `preview`.

- Every `sqlens:format` run now also states whether strict tool mode was on. The line already named the backend, its version, the dialect and the style fingerprint; the strict flag is the remaining parameter that changes what a run *does* rather than how it formats — with it on, a backend the run could not use is a failure, and without it the run says so and carries on. Two machines that exited differently over the same files usually differ there, and the line now shows it instead of leaving it to be guessed. It is printed in both states, unlike the tool version, which is omitted for the built-in core because its absence already says the core produced the output.

## [0.3.0] - 2026-09-05

### Added

- `#[NoSqlOnDriver]` says where a migration's emptiness is deliberate, so `CAP.L0.NOT_CAPTURABLE` stops reporting a decision you already made. A migration that emits nothing on one driver — a partial index is a PostgreSQL feature, a storage-engine change means nothing outside MySQL — annotates the method or the class with the driver and a reason, and the rule stays quiet on exactly that driver. It still reports on a driver you did not name, so the attribute cannot become a blanket switch that merely sits closer to the code, and a misspelled driver name excuses nothing anywhere, which is how the typo shows up instead of quietly disabling the check. Unlike a baseline entry, it moves with the file when you rename it, it sits where the decision was made rather than in another document, and it stops applying the moment the migration becomes empty for some other reason. The reason is required; an empty one is treated as though the attribute were absent.

- A formatter backend can now be asked which version of itself is installed, without formatting a file first. `SqlFormatter::version()` returns the installed version, or `null` when the question cannot be answered — the binary is absent, or it did not respond to the probe. It never throws: a backend is something that improves the output, never something a run requires, so asking about a missing one must not be what fails. The built-in PHP core answers with the package's own version rather than `null`, because it ships inside the package and cannot be missing, and `null` would put the one backend that always works in the same column as the ones that are not installed. Asking repeatedly costs one probe: the answer is a fact about the machine, identical for the first file and the two-hundredth.

### Changed

- **If you implement `CaptureRule` yourself, `appliesTo()` now receives the run's `SubjectContext` as a second argument.** Some capture questions depend on which driver the run is on, and the answer has to exist before a finding does — `evaluate()` must return one, so a rule that decides in there that it should stay quiet has no way to say so.

- **If you implement `SqlFormatter` yourself, you now need a `version()` method.** The interface is the seam behind which a custom backend plugs in, so adding a method to it is a change your implementation has to follow. Returning `null` is a valid answer and the right one when you cannot determine a version.

## [0.2.0] - 2026-09-04

### Added

- `format.binaries.<backend>` takes a third answer: `false` says this project does without that backend. It is a decision rather than a gap, and the run treats it as one — the backend is not named as something that would have been added, and `--strict-tools` has nothing to fail over. A backend that is merely absent is still a loss and still fails a strict run, because the machine that has it formats differently and the output is committed. Naming a switched-off backend is refused rather than substituted, with a message pointing at the key. The built-in core cannot be switched off: it is what makes the suite work with no binaries at all.
- The interpolation rule now reads what the engine's own escaping did to a value, and treats the two forms differently because they are not equally strong. `$connection->escape($value)` is `PDO::quote()` — the result is a value literal that cannot change the statement's grammar or select a different object, which is what a binding gives you at a position that accepts no binding, so the finding goes. `$connection->getQueryGrammar()->wrap($name)` is **not** the same guarantee: measured against both shipped grammars, it stops the breakout (`x"; DROP…` comes back quoted and doubled) and not the object choice (`other_schema.secrets` comes back as two quoted segments). So that finding stays, and only the advice changes — from "pass it as a binding", which no engine accepts for an identifier, to constraining the value to a set you wrote. `wrap()` around a `DB::raw()` is refused outright: an `Expression` is handed back verbatim, so the argument must be provably a string.

- The console summary now names the denominator behind its counts: `summary: 0 fail, 4 undetermined, 0 suppressed — over 32 migrations`. Every number on that line was a numerator, and a numerator alone cannot separate "nothing was wrong" from "almost nothing was read". A consuming project met exactly that: `--path=database/migrations` lints one directory level — because that is what Laravel's own `getMigrationFiles()` globs, so `migrate --path=` does not run the nested migrations either — and a tree of 32 central and 298 tenant migrations reported a clean run and exit 0 over 32 files. The behavior is Laravel's and stays; what was missing was any way to see it. A run whose producer has no file list to count, such as `sqlens:audit`, states no number rather than a misleading zero.

### Changed

- `security.include_vendor_migrations` now decides whether a run READS a package's migrations, not only how it classifies them once it has. Off — the default — a `sqlens:lint` run no longer loads or pretend-executes a migration that ships inside `vendor/`, so a first run after `composer require` can no longer fail on findings inside another package's migrations while reporting nothing about the project's own. The switch keeps its old meaning as well; the setting is one question asked one step earlier. Two runs are deliberately not filtered: one whose paths you named (`--path`, `migration_paths`, `--file`), and `sqlens:predeploy`, because a package's migration really does run during a deploy and can take a lock like any other. If every pending migration turns out to be a package's, the run reports `LINT.SKIPPED.ONLY_VENDOR_MIGRATIONS` rather than an empty result that would read as clean.
- The interpolation finding now names what to do when no binding form exists. An identifier, a schema name, or DDL assembled from an enum takes no placeholder in any engine, so `statement('… = ?', [$value])` was advice that could not be followed there — and with `analyse.exclude_paths` deliberately not reaching the injection rules, a project that could not find the alternative was left with turning the rule off or turning the analyzer off. The alternative existed all along in PHPStan's own `ignoreErrors`, keyed on the rule's identifier and scoped to a path; it is now named in the finding itself, in `extension.neon`, and on both documentation pages. The identifier is derived from the rule rather than written by hand, and a test drives the real analyzer to prove the block removes exactly those findings and leaves every other rule reporting.
- The rule page and the bundled example register both claimed every method the rule looks at takes a bindings array. `DB::raw()` and `DB::unprepared()` do not, and the page's list of fragment methods was also missing `raw`. Both now say what the sink register says.

### Fixed

- A `#[RawSql(reason: …)]` whose reason was wrapped across lines silently answered nothing. Only a bare string literal was read, so `'a ' . 'b'` — the way PHP wraps a sentence, and the way a reason worth writing usually has to be written — left the finding standing while looking exactly like enforcement. Literals joined with `.` are now read as one reason. A constant or a variable anywhere in the expression still refuses the whole of it: reading one would mean evaluating project code during analysis, and that decision is unchanged.
- A derived run context silently lost its `guard_profile`. `RunContext::copyWith()` took the value as a parameter and never passed it on, so every context derived through `withDriftMode()` and its siblings reported a run with no guard profile — a legal state, and therefore invisible from the outside. Found while adding a field beside it, in the one field no test compared.

- `#[RawSql(reason: '…')]` did nothing on an anonymous class, so it did nothing in a Laravel migration — the form every migration has taken since Laravel 9, and where raw DDL usually lives. The rule's own message recommends the attribute, and the only remaining answers were to turn the rule off or to exclude the migrations directory, both of which silence more than the finding. The collector was skipping any class without a namespaced name, which an anonymous class never has; it now joins on the name PHPStan gives it, which is the same name the call site reports. Both placements work: on the class and on the method.

- A database whose name contains `livewire` was read as a production connection, so every database-creating mode refused to run against it — in `local`, and with `--force`, because the production check sits above both. The marker `live` matched it as a segment prefix, and naming the database after the application is what Herd, Valet and `laravel new` all produce. `livewire` is now recognized as a coincidence rather than a marker. The exemption is for that segment alone: `livewire_production` is still production, and every name the obvious alternative cure would have dropped with it — `livedb`, `proddb`, `liveserver` — is still caught. The detector can also name the segment and marker behind a verdict now, so the reason no longer has to be found by removing one segment at a time.

- The shipped config comment for `connection` said `null` means the framework's default connection, full stop. True for capture and lint, and false for `sqlens:audit`, which deliberately does not consult `database.default`: with more than one supported connection it refuses and lists the candidates, because which instance was read is part of what the report asserts and a primary and its replica disagree about settings, about lag, sometimes about schema. A project meeting that refusal had no way to anticipate it from the file it had just configured. The comment now states both halves, and one test reads the block out of the shipped file while driving the resolver, so the prose and the behavior cannot drift apart again.

## [0.1.0] - 2026-09-03

The first public release. Nothing before it ever shipped, so there is no earlier version for any of this to be a change *from* — read the sections below as a description of what the package **is**, not as a diff.

### The shape of it

SQLens is a database safety toolkit for Laravel applications on PostgreSQL 18+ and MySQL 8.4+. It reads the migrations you are about to run and the schema you already have, and it says what they will cost.

Three principles govern every part of it, and they are worth stating first because they explain most of the design decisions further down.

**No silent green.** Every result is one of three values — `pass`, `fail`, `undetermined` — never two. A check that cannot run is reported as `undetermined` with a named reason, never folded into the passing set. On a managed database, where a great deal of the catalog is simply not exposed to any role you can hold, that third value is the normal answer rather than an edge case, and a tool that hid it would be reporting a clean bill of health for questions it never asked.

**Primum non nocere.** The tool must not harm the database it is pointed at. It takes no lock of its own, issues no write, and reads catalog and state views only. It sets its own session timeouts so it cannot become the thing that hangs. It keeps no state in your database at all — the migration debt account is a file in your repository, not a table. The two modes that do create a database create a throwaway one, and both sit behind a production guard that refuses by default.

**Determinism.** The same state produces the same result on a developer's machine and in CI. That is held by the `assume_server_version` pin, strict tool mode, and a canonicalization layer every rule works on rather than raw SQL. There is deliberately no "fast" path that disagrees with a "correct" one.

### Added

**Eleven commands.**

- **`sqlens:lint`** — reads the migrations that have not run yet and reports what they will do to a live database. It obtains their SQL through Laravel's own grammar rather than by parsing your migration source, so the advice is about the statement your app will really send: by default without executing it (`--pretend`), or by running it against a throwaway shadow database it creates and drops itself (`--shadow`). `--roundtrip` replays up, down and up again in that shadow database to test whether `down()` is a real inverse. A single-file fast path (`--file`) needs no database at all and is built for a pre-commit hook.
- **`sqlens:audit`** — reads the catalog of a database that already exists and judges the schema as it stands. It will not guess which connection, which read host, or which tenant the report is about: where the configuration leaves a choice, the run stops and says so rather than describing one server under another one's name.
- **`sqlens:security`** — roles, grants, transport, server configuration, row-level security, injection and unencrypted columns, across every suite. Gated by a severity axis of its own rather than by the strictness level, so lowering the level band cannot silence it.
- **`sqlens:predeploy`** — reads the target database immediately before a deploy: read-only, fail-closed, and bounded by a time budget so it can never be the thing that hangs a release. It checks what the migration is about to walk into — a lock blocker, replication lag, disk headroom, a missing privilege, a read-only target, a version skew.
- **`sqlens:postdeploy`** — reads what the deploy left behind: an index that ended up invalid, a constraint that was never validated, an orphaned transition object. Read-only, catalog-only, once.
- **`sqlens:drift`** — compares what the database holds against what the migrations describe, with an exclude file for the differences a project has accepted, each needing a reason.
- **`sqlens:baseline`** — writes the findings of today into a file you commit, so a project can adopt the tool on a schema it inherited without a red build on day one.
- **`sqlens:format`** — one house style for the SQL in your migrations, with a `--check` mode a CI step can act on and a `--diff` mode that shows what a write would do without doing it. Three backends behind one seam; the built-in one needs nothing installed.
- **`sqlens:doctor`** — what SQLens can actually see from here: each connection's real server version, and each optional tool's version or its absence. An absent tool's line names what you lose by not having it rather than merely reporting it missing.
- **`sqlens:mcp`** — serves the same engine the commands use to an AI agent over stdio. Every tool is read-only unless named individually with `--enable-tool`; there is deliberately no option that enables them all.
- **`sqlens:agent-rules`** — writes the project's active rule set into its coding agents' context files, so an agent knows a rule before it writes the migration rather than after the linter rejects it. Opens no database, and its `--check` mode treats a missing artifact as a deviation rather than creating it.

**225 rules, every one of them documented.** The catalog ships as a data artifact with a published page per rule id, and the count is held rather than claimed: 225 entries, 225 pages, zero pending. Every finding carries the URL of its own page, derived from the rule id rather than written by hand, so a link a shipped finding already carries cannot drift.

By category: 135 safety, 57 security, 17 idiom, 7 performance, 6 convention, 3 privacy. By maturity: 220 stable, 3 preview, 2 experimental.

**Ten cumulative strictness levels, and the level is an appetite rather than a severity.** Level 4 runs everything up to 4. The distribution is deliberately front-loaded — 136 rules sit at level 0, and the bands above it add taste rather than danger. Level 6 tells you about choices a reasonable engineer might have made on purpose, and reading that band as a defect list is the commonest way to misread it.

**A maturity axis that keeps a minor release from breaking your pipeline.** A new rule lands as `preview` and runs only on request. An unconfigured project gets stable rules only — the opposite default to categories, where unconfigured means all, and the difference is the point: an unset category axis means nobody expressed a preference, an unset maturity axis is the versioning promise doing its job.

**A `downtime_class` on every finding that can change a statement's locking behavior** — `online`, `blocking` or `rewrite` — so a deploy script can ask whether this release needs a maintenance window without knowing which rules carry the answer. 58 entries carry one: 38 rules and 20 deploy checks, distributed 38 online, 18 blocking, 2 rewrite. The rest carry none because the question does not apply to them — a run notice describes the run, and a rule that only reads the catalog is not about a statement that takes a lock. The JSON envelope exposes the worst one in the run directly rather than making a consumer re-derive an ordering that is this package's judgment and is not alphabetical.

**A severity axis of its own.** 78 of the 225 entries carry a severity: the 58 security and privacy rules, which answer to it instead of the level gate, plus 19 deploy checks and one debt notice, where a severity orders several failures rather than gating any of them. Across all of them: 7 critical, 32 high, 28 medium, 8 low, 3 info. The other 147 entries answer to the level gate. The two gates are never merged — a strictness choice and a security risk are different facts, and one number cannot carry both.

**Five reporters over one result** — console, JSON, GitHub annotations, SARIF, and an agent format — plus registration for a custom one. The SARIF output is validated against the real schema rather than eyeballed, over a populated run, an empty one and a catalog-only one.

**A four-value exit-code contract** a pipeline branches on: clean, findings above the gate, misconfiguration, and undetermined under strict mode. Misconfiguration beats everything, including a run with no findings at all, because a tool that cannot trust its own setup must never report green.

**A pre-scan that refuses to execute a migration it cannot execute safely.** A migration that sends mail, calls an HTTP endpoint, guards on introspection, or reaches its effect through your own code is reported and never pretend-executed. Recognizing a side effect is not the same as preventing one, and the honest move is to decline rather than to run it and hope.

**A migration debt account.** The two-step patterns this tool recommends — expand then contract, add then validate — leave a second step somebody has to actually take. The ledger is a file in your repository that records which ones are outstanding, how long they have been, and which have since been resolved. It is a repository file rather than a table on purpose: a safety tool that writes to the database it is auditing has given up the property that makes it safe.

**A supported-version floor that qualifies the report instead of withholding it.** Below the floor the run still produces its findings and says unmistakably what they are worth — a named `undetermined`, a marker in the run header, and a failing exit under strict mode. The message states that findings may be wrong in both directions, because the one-sided reading misses the dangerous half: below the floor no rule was ever written for the hazards that only exist there, so a clean report is the least informative result the tool can produce rather than the best one.

**A bundled Laravel Boost skill**, so an assistant working inside a consuming application has the adoption guidance without being told where to look.

### Security

The package connects to production databases and shells out to external binaries, so its own posture is part of what it ships rather than an implementation detail.

- **It takes no lock of its own, and writes nothing to the database it is pointed at.** Every read goes to a catalog or state view. The two modes that need to execute a migration — `--shadow` and `--roundtrip` — do it in a throwaway database they create and drop themselves, never in yours, and both refuse to run against a production connection unless the guard is explicitly lifted. The one network call in the package is `sqlens:security --refresh-advisories`, which is never a side effect of a check and runs before anything connects.
- **Credentials are redacted from every output** — reports, the JSON envelope, the agent artifacts and the debt ledger.
- **The MCP server is read-only by default.** A mutating tool is exposed only by being named, one at a time.
- **Database-creating modes sit behind a production guard** that refuses by default and reports which of its three checks held a blocked run, because the three need different fixes.
- **A dedicated read-only audit connection is supported**, so the role that reads your catalog need not be the role your application runs as.

### What 0.1.0 does not do

- **The public API is not frozen.** It is documented, and it is what a 1.0 will commit to, but a field or a flag may still change in a minor release before then.
- **PostgreSQL and MySQL only.** MariaDB is refused by name rather than half-supported: it answers Laravel's `mysql` driver and does not share its semantics, and the divergences are exactly what this tool reasons about — so advice about it would be confident, specific, and about another product. SQLite and SQL Server are declared non-goals for the same reason.
- **One shipped locale.** Everything this package emits goes to a terminal, a CI annotation, a SARIF file or an agent artifact, and a translated `ALTER TABLE` warning still contains `ALTER TABLE`.
- **Statistics-dependent rules are opt-in and honest about it.** The index-usage rules answer from counters that can be reset, so they ship `experimental` and report nothing until you ask for them. The source-reading pre-scan detectors ship `preview` for the same reason.
- **Levels 8 and 9 are thin** — 4 and 6 rules. The convention band is defined and only lightly populated.
- **The MCP server cannot shield standard output from what precedes it.** It takes the channel as early as a service provider can, diverts stray writes to the diagnostic stream and keeps `stdout` for protocol frames — but a message PHP emits while loading a file happens in the autoloader, before any provider boots. A host application whose dependencies emit a compile-time deprecation can therefore corrupt the frame stream, and no code inside the server can intercept it. The client reports a protocol error; the cause is on the other side of the boundary.
