# Changelog

All notable changes to `pushery/sqlens-for-laravel` are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.0.0/) and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.17.0] - 2026-09-16

### Fixed

- **A functional index on MySQL is now compared instead of skipped, the same way it already was on PostgreSQL.** `CREATE INDEX ... ((lower(display_name)))` came back understood on one engine and as a `not_understood` skip on the other, and nothing said whether that was a limit of MySQL or of this package's reading. It was the reading. Measured against a real MySQL 8.4.10: `information_schema.STATISTICS` returns one row per key position, with `COLUMN_NAME` null and `EXPRESSION` filled on the expression part — the same shape PostgreSQL's per-position `pg_get_indexdef()` produces. The reader was already asking for `EXPRESSION` and then set it aside, recording it beside the index with a flag saying so, and the comprehension check believed the flag over the key list. The expression now enters the key list, so a redundancy question about a functional index is answered rather than declined. **Expect findings you have not seen before**: an index this package used to decline to reason about is now one it reasons about, and on a schema with functional indexes that is new output, not a regression. The flag remains as a fact about the index, beside `visible` and `prefixed_columns`. The same measurement found a second defect: for `KEY (a, (lower(b)))` the expression was read off the index's leading key part, which carries none, so an index that plainly had one reported `null` — it is collected across the key parts now.

## [0.16.0] - 2026-09-16

### Changed

- **Two absences in the rule set are now stated rather than left as gaps.** MySQL's `--skip-grant-tables` gets no rule, because the server enables `skip_networking` alongside it and therefore refuses every remote connection — a run that connected at all proves it is not in that state, so the rule could never have a subject. And there is no composite id for a `pg_hba.conf` line that authenticates with `password` on a server whose `ssl` is off: `SEC.AUTH.HBA_CLEARTEXT` and `SEC.PG.TLS.DISABLED` are both already in the report on exactly those runs, and a third id would only restate their conjunction. Both reasons now sit where the question comes up, on the scope page and beside the rule.

### Fixed

- **On MySQL, `sqlens:predeploy` no longer judges the server settings when no migration is pending.** MySQL ships `lock_wait_timeout` at one year, which this check reports as an unbounded wait at `high` — and the MySQL side never asked whether anything was about to run, so every deploy on a server at its defaults stopped over it, including the ones that carried no migration at all. The messages argued from "a migration is about to run" either way. It now makes the split the PostgreSQL side has made since 0.11.0: with nothing pending every variable is `not_applicable` with the reason `nothing_pending`, named with its value and without the sentence about the change; with a migration pending nothing changes. The provenance note stays a `pass` in both cases, because it describes the reading, not the change.

## [0.15.3] - 2026-09-16

### Fixed

- **`sqlens:predeploy` stops a deploy only for a `high` server setting; the lower ones are reported beside a passing result.** Every finding of `DEPLOY.CONTEXT.SETTING` blocked, whatever its severity, and a consumer hit the cost on a managed PostgreSQL: a deploy with a pending migration was refused over `statement_timeout = 0`, which cannot be set server-wide without bounding the very migration the deploy runs, and over `max_wal_size` at its default, which such a host does not let anybody change. The rule's own page called both "reported rather than judged". Now `high` stops the deploy — `lock_timeout = 0` on PostgreSQL, and `lock_wait_timeout`, `foreign_key_checks` and `sql_mode` on MySQL — while `medium`, `low` and `info` travel as `pass` findings with their values and sentences. On MySQL that also ends a deploy stopped by nothing but the `info` note about a role that cannot read `performance_schema`. A `lock_timeout` set with `SET` inside a session still does not clear the finding, because the check reads what a fresh session gets; a role default does.

## [0.15.2] - 2026-09-15

### Fixed

- **The MCP handshake answers the one revision this build speaks, or it refuses — it never negotiates a third one.** A client asking for a revision SQLens does not implement was being served `2025-11-25` instead of a refusal naming `2025-06-18`, which is the quiet direction this pin exists against: the client gets a message shape it did not ask for, cannot check, and has no reason to doubt. The refusal is back, by name and with the supported revision in it, exactly as before. A revision substituted for the pinned one is now refused as well, rather than served — a server that announces a revision it does not implement is worse than one that will not start.

### Changed

- **The dev toolchain carries `laravel/mcp`, `laravel/ai` and `laravel/boost`.** They sit in `require-dev`, so nothing a consumer installs, calls or configures changes, and a Renovate rule keeps their constraints following each release.

## [0.15.1] - 2026-09-15

### Fixed

- **A partial index on a number is read: `WHERE tenant_id = 1` was not.** The predicate model refuses *"a comparison against a non-literal"*, and its literal pattern was quoted-only — so an equality against a number fell under that sentence while meaning nothing of the kind. A number is exactly as unambiguous there as a string, and `tenant_id = 1` is the partial index of a multi-tenant schema. Under `--profile=ci` each one was an `undetermined`, which `strict_undetermined` turns into exit 3.

  **Found before it was reported.** Twenty-two realistic partial indexes were created on a real PostgreSQL 18, their printed predicates read back and put through the parser: sixteen read, six refused — and only one of the six was a gap. The other five are refusals the model states on purpose: an ordering comparison, the pair a `BETWEEN` prints, an `OR`, and a jsonb operator.

  Equality, inequality and their `ANY`/`ALL` set forms now take a number, in the parenthesised cast shape the server prints inside an array (`(1)::bigint`). **An ordering comparison stays refused**, and an arm holds that in four spellings — without it the widening would have traded the defect for its mirror image, because two indexes at `> 100` and `> 99` are not the same index and would now look it. Every new shape is in the corpus the PostgreSQL lane checks against a live server.

- **A partial index whose excluded values carry their own cast is read instead of refused.** PostgreSQL prints the same `NOT IN` predicate two ways depending on how the migration wrote it: the cast on the whole array — `(ARRAY['a'::character varying])::text[]` — or on each member inside its own parentheses, `('a'::character varying)::text`. The first was read; the second was not. Stripping the casts left `('a')`, which is no longer a literal, so every member failed to parse and the whole predicate came back `not_understood`.

  That is not a cosmetic refusal. Under `--profile=ci` the `strict_undetermined` policy escalates an undetermined verdict to exit 3, so a consuming application whose entitlement index carries this shape could not get a clean run — and the three ways out were all worse than the defect: suppressing the reason would have silenced **every** unreadable catalog row rather than this one, no per-rule configuration exists, and rewriting a correct index for a reader's benefit puts the tool above the thing it inspects.

  The literal is now unwrapped the same way a parenthesised column reference already was, and for the same reason: the parentheses belong to a cast that has just been removed. One literal and nothing else between them — `('a' || 'b')` keeps its parentheses, because dropping them there would change what the text says.

  **The shape was read back from a real server, not typed from a report.** The shared predicate corpus that both the unit suite and the PostgreSQL lane consume carries it now, so the day the server prints it differently the lane says so. The reported index appears in the regression set **twice**, once in each printing, because the pair is the finding: the refusal was about the printing, never about the predicate.

## [0.15.0] - 2026-09-15

### Added

- **A catalog finding can point at the migration that introduced its subject.** A lint finding knows its file and line because it reads migrations; an audit finding reads a DATABASE, and the database has never heard of `2024_01_11_000000_create_orders_table.php` — it knows `public.orders.customer_id`. So an audit finding landed in a log while the person reading the pull request was looking at the migration diff, and a finding in a log is one somebody has to go looking for. The anchor is resolved by reading `database/migrations` the way the rest of the package reads migrations — parsed once, never included, no connection and no migrator — and a finding that gets one now carries the file and the line of the call that created the table or the column.

  **Both output paths carry it.** `--format=github` puts the annotation on the migration's own line, so it lands in the diff of the pull request rather than in a log; SARIF uses the migration as the alert's physical location, with its real line. What does not change is the subject: the object stays in `logicalLocations`, the physical location is still flagged `sqlens-anchored`, and a new `sqlens-anchor-kind` distinguishes a real migration from the configured stand-in used when there is none. A migration is where an object came FROM — the finding is about the object as the database holds it now, and a `CREATE TABLE` that was correct on the day it ran is the ordinary case. Both reporters say that in the message rather than leaving a reader to infer it from a file name.

  **Every failure is an ABSENT anchor, never a wrong one.** A table named by a variable or a constant, a file that will not parse, a project that has run `schema:dump --prune` and has no migrations left to read: all of them answer nothing, and the finding is reported exactly as it was before, without a file and a line. That asymmetry is deliberate — a missing anchor costs a reader one search, and a wrong one sends them to edit a file that had nothing to do with the finding. It is the same reason the scan will not resolve `self::TABLE` by reading the class: it could, and each place it would have to look is one more place to be confidently wrong.

  **It is presentation, and that boundary is held rather than promised.** The anchor never changes a severity, a downtime class or whether a finding stops a build, and it never enters a fingerprint — a renamed or moved migration must not invalidate a baseline entry, because the database that entry describes did not change when somebody moved a file. Two smaller decisions are worth naming: the first writer wins, so a table created once and altered three times anchors to its creation rather than to its last edit; and the table a column belongs to is tracked by nesting rather than by the receiver's name, so a migration that calls the builder `$t` is read like every other one. The resolved path is `database/migrations` alone, which is a deliberate floor — the full set needs the application's migrator, and a rule that reached for the container would stop being answerable from a bare project root. A package that registers its own migration path simply yields no anchor, reported the same ordinary way as a squashed schema.

- **A narrowing foreign key carries fix material, not just a sentence.** `PG.L9.TYPE_IMPLICIT_CAST` reports a key whose two ends are different types, and for the one shape with a dated failure — a single-column key whose referencing side is a narrower integer than the key it points at — the only suggestion it gave was prose in the message. It now carries a machine-readable payload, so the agent reporter, the GitHub reporter and `capture` all have something to hand on. The sequence is expand/contract, every step its own migration: a wider column beside the old one, a backfilled job, a release writing both, the constraint moved, the old column dropped last. `ALTER TABLE … ALTER COLUMN … TYPE bigint` reaches the same end state in one statement and is named in a precondition rather than emitted — on PostgreSQL it rewrites every row under `ACCESS EXCLUSIVE`, blocking readers as well as writers, and the size at which that stops being acceptable is a fact about your table. The other shapes reach a considered `none` rather than silence: a composite key, whose columns cannot be widened one at a time without deciding an order; a pair where the referenced key is the narrower side, where matching them means moving the parent; and a pair that is not two widths of one number, where the right answer depends on which side is telling the truth about the data. The MySQL rule offers no material and its page says why: the server refuses the narrowing integer pair outright when the key is created, so that shape never reaches a MySQL catalog. A pair whose verdict is UNDETERMINED carries nothing: a table whose only mismatched key has an end the catalog could not read is reported as undecided, and material beside that would read as advice about the thing the rule just declined to judge.

- **A table somebody switched autovacuum off for is reported: `PG.L7.AUTOVACUUM_DISABLED`.** `ALTER TABLE … SET (autovacuum_enabled = false)` is sometimes the right call — a table bulk-loaded on a schedule is vacuumed better at a chosen moment than at an arbitrary one — and what makes it worth a finding is that the decision outlives the reason and nothing else in the database mentions it again. Two consequences, and the second is the one that surprises: dead rows are not reclaimed, so the table's file size stops saying anything about the rows a rewrite would copy and its row estimate goes stale with it (autovacuum is what triggers most `ANALYZE` runs); and the setting **does not avoid the vacuum**, it defers it — when the table crosses `autovacuum_freeze_max_age` the server starts an anti-wraparound vacuum on it regardless, that worker does not yield to a lock request, and by then there is more to do. `DEPLOY.PREFLIGHT.FREEZE_HORIZON` is the deploy-time half of the same fact.

  Three states are read out of `pg_class.reloptions` and only one is reported: `false` is the finding, `true` is somebody being deliberate the other way, and **absent** — the ordinary case — means the table runs under the cluster's setting. The value is kept as the server's own spelling rather than cast to a boolean, because a boolean has no third value and the third value is the common one. A hand-maintained table is a real false positive and the finding says so: this check cannot see the cron that vacuums it, so the answer is an `ignore` entry with the reason beside it rather than a heuristic guessing at intent from a name or a size. PostgreSQL only — InnoDB has no per-table equivalent, and `STATS_AUTO_RECALC` decides whether optimizer statistics are refreshed, not whether dead rows are reclaimed.

- **The deploy report names an autovacuum-off table it is about to touch: `DEPLOY.PREFLIGHT.AUTOVACUUM_DISABLED`.** The audit rule above reports every such table in the database, which is the right shape for an audit and the wrong one for a deploy — the list is read once, and somebody planning a migration has no reason to go back to it. This check asks the narrower question at the moment it matters, and it adds a consequence an audit cannot state: **the run's own estimates for that table are the least trustworthy figures in the report.** A table without autovacuum keeps its dead rows, so its file size stops predicting what a rewrite would copy and its row estimate goes stale with it, and every duration and size stated here for it is derived from exactly those two numbers. The second consequence is the one `DEPLOY.PREFLIGHT.FREEZE_HORIZON` measures from the other end: the setting defers the vacuum rather than avoiding it, and the anti-wraparound worker that eventually arrives does not yield to a lock request.

  It looks at **every** table the pending statements name as their subject, whatever they do to it — deliberately wider than the lock-shaped checks beside it, because a stale estimate spoils the numbers for any statement whose cost the report estimates, not only for one taking an exclusive lock. A table a statement merely refers to is left alone. It reports at a fixed `medium`: it does not stop a deploy, so reporting it beside a finding that does would teach a reader to discount both, but it changes what every other number for that table is worth. A hand-maintained table is exempted with an `ignore` entry and its reason — the cron is not in the catalog, and a heuristic guessing at intent would silence the common case to spare the rare one. PostgreSQL only.

- **A migration's column definitions reach the rule layer, so a lint rule can ask what a column IS.** They never did: `keyColumns` carries an index's key, not a type, and the body a `CREATE TABLE` writes was not looked at. Every rule whose judgment needs a column type was therefore **structurally audit-only** — not because that was the right answer, but because the question could not be put. The catalog answers it once the table already stands; the migration that introduces a wrong type is the cheapest moment to fix it. Both grammars are read: the parenthesized body of a `CREATE TABLE`, and the trailing type of an `ALTER TABLE … ADD COLUMN` — including MySQL's bare `ADD` form, which is the one Laravel actually emits.

  **The type goes through the same normalizer the catalog reader uses**, and that is the part that makes the two comparable rather than merely similar: `CanonicalType::fromRaw()` already speaks both vocabularies, so a migration's `bigserial` and the catalog's `bigint` land on one name, as do `varchar` and `character varying`. There is no mapping table in this layer and there must never be one — two normalizers would be two answers, and a lint verdict and an audit verdict about one column have to be the same verdict.

  **All or nothing, and null rather than empty.** A member whose shape the reader does not recognize declines the *whole* body: a rule handed nine columns out of ten cannot tell one is missing, and the finding it then makes is wrong in the silent direction and permanent. An empty list is never produced, because a table with no columns is not a thing — so null means "nobody read one here", which a rule turns into silence or `undetermined`. The same distinction runs one level down: a column whose type could not be read arrives **present** with a null type, because "this column is absent" and "I could not read its type" are different answers.

  One discriminator is worth naming because an arm found it rather than review: **a column name is quoted** after identifier normalization, and a bare word opening a member is not one. `CREATE TABLE clone (LIKE users INCLUDING ALL)` is a real body member that brings columns this reader cannot see, and `LIKE` is in neither driver's keyword list — so without the test it arrived as a column *named* `like`, typed `users including all`. Adding `LIKE` to the keyword lists would fix it and cost a canonical form-version bump, which moves every fingerprint and baseline entry in every project. A user-defined type is unaffected: there the name is quoted and only the type is bare. The keywords that end a type belong to the **driver**, because `CHARACTER VARYING` is a type on PostgreSQL while `CHARACTER SET` is a modifier on MySQL.

- **A `lock_timeout` that is not smaller than `statement_timeout` is reported: `PG.L3.LOCK_TIMEOUT_INEFFECTIVE`.** The two clocks bound different things and one of them is nested inside the other — `lock_timeout` the wait in the lock QUEUE, `statement_timeout` the whole statement including that wait. Set the second to a number the first cannot reach, and equal is already too large, and the statement is aborted before the lock wait ever gets to its own limit: the lock clock is configured, visible and dead. The configuration reads like a safety net because both values are set and both are non-zero, and **the failure afterwards is mislabeled as well** — the statement comes back as a *statement* timeout, so whoever reads the log concludes the DDL is slow and goes looking at the table, when the migration never got the lock at all. Two diagnoses, opposite ends of the problem. This package recommends both clocks in its own remediation preamble and justifies them by exactly this difference, so an arm proves the shipped template can never produce such a pair: every step it emits carries a placeholder rather than a value, so there is no pair of numbers in it to be wrong.

  **It judges `reset_val`, not `setting`, and getting that wrong would have made the rule judge SQLens.** This audit sets both of these timeouts on its own session before it reads anything, so the session value describes the tool on every server it is ever pointed at. `reset_val` is what the configuration file, the database and the role have settled between them — the pair a fresh deploy session inherits before it sets anything itself. Which layer named either clock is measured beside it from `pg_db_role_setting`, because `pg_settings.source` answers about the reading session and a reader told the pair is wrong still has to choose between `ALTER DATABASE`, `ALTER ROLE` and `postgresql.conf`; neither clock appearing there is a measured answer and says the pair came from the file or the default. Two states are deliberately not reported: `lock_timeout = 0` is unbounded rather than ineffective and is already `PG.L3.MISSING_LOCK_TIMEOUT`'s finding, and `statement_timeout = 0` means there is no statement clock to abort first. MySQL gets no twin — `max_execution_time` applies to read-only `SELECT`s so it cannot abort this DDL, and `lock_wait_timeout` and `innodb_lock_wait_timeout` are separate clocks with separate reach rather than one nested in the other.

- **The shipped registry holds 237 entries**, three more than 0.14.0. By category: **143 safety**, 58 security, 17 idiom, **10 performance**, 6 convention and 3 privacy. By maturity: **232 stable**, 3 preview, 2 experimental. **157** answer to the level gate; the other **80** carry a severity — 7 critical, 32 high, **29 medium**, 8 low and 4 info. None of the three carries a `downtime_class` — nothing here is a schema change, the preflight check reports on the trustworthiness of an estimate rather than on an operation, and the timeout pairing is a statement about configuration — so that count stays at 58 entries.

### Fixed

- **Thirty-three rule pages said nothing about fix material the package hands over on every report.** Each rule page carries a generated block naming the sequences that rule's payload can offer, and the derivation behind it started by asking whether the rule's source text contained `ProvidesRemediation`. `ProvidesSchemaObjectRemediation` — the seam a catalog rule offers its material through — does not contain that substring: after `Provides` comes `Schema`. Every rule on that seam therefore fell out of the derivation before its first line, and its page stayed silent. The silence is worse than an omission, because the lint rules' pages all say it: a reader who knows both kinds of page concludes from the absence that there is nothing to hand over, and leaves a payload on the table. `PG.L5.COLLATION_VERSION_MISMATCH` ships a complete `reindex_before_refresh` sequence and its page did not mention it.

  **The filter now asks the type rather than the text**, and the strategies are read from the whole class hierarchy rather than from one file. That second half matters as much: a lint rule constructs its template in its own body, but the entire server-setting family reaches `NoSafeSequenceTemplate` through its base class and `OffersAConsideredNone` is a trait — so reading only a rule's own file answers "offers nothing" for thirty-one rules that each offer a considered `none`, which is a conclusion rather than an absence and is exactly what the page exists to print. Measured when the derivation changed: all forty-two rules already in the map kept their exact strategy list, and thirty-three joined them.

  **Two guards were green over this the whole time, and both are sharper now.** The page check's ground set was the derivation itself, so it confirmed completeness over a set the missing rules were never in. The anti-vacuity control was a threshold over the union — `count > 30`, which forty-two lint rules clear comfortably — so it could not distinguish a healthy map from one with a whole seam cut out of it; it is now held per seam, and whichever seam disappears, the arm names it. A third arm holds the set of rules that *inherit* their seam non-empty, which is the state no text filter can reach: any derivation that reads a rule's own source again reports zero there, and zero fails.

## [0.14.0] - 2026-09-14

### Changed

- **A PostgreSQL row estimate now says how far the table has drifted since the statistics were taken, not only when they were taken.** The age alone cannot tell a reader whether a number still holds: a statistic from a year ago on a table nobody has written to is exactly right, and one from an hour ago on a table that doubled since is out by a factor of two — and both render identically as a timestamp. The statistics reader picks up `pg_stat_all_tables.n_mod_since_analyze` on the join it was already making, and the console narration reports it as a ratio of the estimate (`1.5x` means half again as many rows changed as the estimate claims the table holds). It is not clamped, because a table that turned over three times is the case that matters most; an estimate of zero rows reports no ratio rather than dividing by nothing. **Silence means not counted, never "nothing changed"** — every size estimate is in that state, and so is every MySQL reading, because InnoDB keeps no counterpart figure and its `last_update` answers the question the age already answers. The drift is advisory prose and deliberately does **not** appear in the JSON report or in the stable rendering a determinism digest is taken over: a new key in either would be a schema change and a new digest for every unchanged database.

- **A server setting whose change is waiting for a restart is no longer reported as fine.** PostgreSQL's `pending_restart` says somebody already changed a value, the server accepted the change, and it applies at the next restart — so from that moment the running value and the decided value are two different things, and only the running one is in the catalog. Every server-baseline rule read that flag through the subject and none of them asked about it. A setting that is correct **right now** and carries a pending change is now `undetermined` with the new reason `setting_change_pending_restart` rather than a silent pass: a green that expires at the next minor upgrade or failover is a green nobody scheduled. A value that is **already wrong** is still reported as wrong, with the pending change added to the finding rather than replacing it — the problem is present-tense either way, and a reader fixing the running value needs to know the configuration file already says something else. The run names the running value and says why it cannot name the other one: the decided value lives in the file, not in `pg_settings`. **MySQL is untouched** — it has no counterpart, and the reader reports `null` there rather than `false`, so only an explicit `true` produces any of this.

  **Upgrade:** `setting_change_pending_restart` is a new value in the undetermined reasons of the JSON report. Under `strict_undetermined` — which `--profile=ci` sets — a server with a pending change now moves the exit code where it previously did not. That is the finding doing its job; suppress it per variable through `ignore` if the change is deliberate and waiting for a maintenance window.

### Added

- **A polymorphic column pair with no index over it is reported: `PG.L5.MORPHS_NO_INDEX` and `MY.L5.MORPHS_NO_INDEX`.** A polymorphic relation resolves by BOTH columns at once — `commentable_id = 7` names a post, an invoice and a user, and only `commentable_type` says which — so every access through the relation constrains the pair. Without an index over it each of those reads the whole table, and the cost grows with the table rather than with the number of relations. Nothing in the schema hints at it: a foreign key at least announces the relationship it belongs to, while a polymorphic pair is two ordinary columns whose meaning lives in the application. `morphs()` writes the index along with the columns; hand-written columns and a `nullableMorphs()` that a later migration replaced with its two parts regularly do not.

  The **order** is part of the finding. A B-tree serves a left prefix, so an index leading with the type column answers both the paired lookup and a type-only one, and one leading with the id answers the pair and an id-only lookup nothing performs. An index the wrong way round is therefore reported as its own sentence — *replace this index* rather than *add one*. Told merely that no index exists, a reader adds a second index over the same two columns, and `PG.L7.INDEX_REDUNDANT` then reports that.

  Both rules are **audit-only, and structurally so**: the judgment needs the type of both columns, and a `CREATE TABLE` statement carries none. The pair is identified by naming, so a `<prefix>_type`/`<prefix>_id` pair that merely happens to be named that way is a false positive by construction and belongs on the ignore list — the catalog can prove the columns exist and what they hold, never that `morphs()` wrote them. The id side deliberately does not accept `varchar` or `text`, which Laravel never writes for a morph id, and does accept the `char(36)` and `char(26)` that `uuidMorphs()` and `ulidMorphs()` write.

  Unlike the foreign-key rule, this one exists on **both** engines. `PG.L5.FK_NO_INDEX` has no MySQL twin because InnoDB creates that index itself; measured against 8.4, it does nothing of the kind here, because a polymorphic pair is not a declared relationship and the server has never been told the two columns belong together.

- **A deploy is warned when a table it locks is near its freeze horizon: `DEPLOY.PREFLIGHT.FREEZE_HORIZON`.** An ordinary autovacuum yields to a conflicting lock request and the `ALTER TABLE` behind it proceeds. One running to prevent wraparound does not: it holds its lock to the end, because the alternative is a cluster that stops accepting writes. On a large table that is hours, and from outside it does not look like a lock at all — `pg_locks` shows your statement waiting, the holder is a background worker, and the deploy simply does not move.

  The check reads **both** freeze clocks for the tables the pending run will lock, and holds them against the thresholds the **server** carries rather than hard-coded numbers. The second clock is the one nobody watches: multixacts are consumed by **locking**, not by writing — one is created as soon as a second transaction locks a row somebody else already holds, which is the ordinary state of a foreign-key check — so a lock-heavy table can be spotless on the transaction clock and be the table that stops the cluster. A worker already running is named with its phase and block progress from `pg_stat_progress_vacuum`, and the finding says explicitly **not** to cancel it: the launcher starts it again within `autovacuum_naptime`, the work done is thrown away, and the horizon is closer than before. A run that also rewrites a table is told that this makes the window longer rather than shorter. Where the views are withheld — the normal case on a managed instance — the answer is `undetermined` with `freeze_horizon_unreadable`, never silence. PostgreSQL only: InnoDB has no visible freeze horizon.

- **The shipped registry holds 234 entries**, three more than in 0.13.0: the two rules and the deploy check above. By category: **141 safety**, 58 security, 17 idiom, **9 performance**, 6 convention and 3 privacy. By maturity: **229 stable**, 3 preview, 2 experimental. **155** answer to the level gate; the other **79** carry a severity, unchanged at 7 critical, 32 high, 28 medium, 8 low and 4 info. None of the three carries a `downtime_class` in the catalog, so that count stays at 58 entries.

## [0.13.0] - 2026-09-13

### Fixed

- **A server finding withheld on a disposable database now names a command that judges it.** Under `security.server.lifetime = disposable`, the not-applicable note said the server fact is judged by `sqlens:predeploy` on the host that will be operated, and `sqlens:predeploy` runs no `SEC.*` rule at all: a project that followed the note had its server security checked nowhere. The note now names `sqlens:security` and `sqlens:audit`, which run all twenty of these rules, against the host that is actually operated, and the security suite page says the same.

- **The published `config/sqlens.php` writes US English.** A consuming application whose US-spelling guard reads its published config had to exempt the whole file over British spellings in its comments, and with the exemption its own comments in that file went unread too. The comments now say `artifact` and `analyzes`, the suite names are code-formatted where the prose lists them, and the same spelling reaches the shipped messages, the rule pages and the escalation register. ### Fixed

- **An expression index with a comma inside it is compared, and an index compared inside its own universe is no longer reported as not compared.** `COALESCE(heading, '')` is one key position, and PostgreSQL prints it with the comma inside the call. The reading split key positions and member lists on every comma and semicolon, so the expression arrived in pieces and the index was reported `not_understood`; both lists are now split only outside parentheses and quotes. Text that does not balance, a closing parenthesis with nothing open included, is still split at every separator, so one broken entry cannot fold the members after it into itself. Separately, a GIN index alone under its method and operator class, and a partial index alone under the only condition on its table, were reported as not compared although every comparison that means anything had been made, and a strict pipeline turned those notices into a permanent red. A notice now appears only where a comparison really went unmade: a condition the reading cannot group, a partial index whose table carries a different condition, a b-tree under a non-default operator class, an expression that did not arrive whole. Reported from a consuming application whose search index, full-text index and one partial index read "unknown, not fine" on every run.

  **Upgrade:** expect fewer `AUDIT.CATALOG.UNREAD.NOT_UNDERSTOOD` notices, and possibly a new `PG.L7.INDEX_REDUNDANT` finding where two expression indexes holding a comma really are redundant, because they are now compared.

- **`PG.L7.INDEX_REDUNDANT` no longer calls one of two partial indexes a duplicate when only their operator class differs.** Two partial indexes under the same condition were compared on their key positions, and PostgreSQL prints a key position without its operator class: `(email text_pattern_ops) WHERE state IN ('closed', 'void')` and `(email)` under the same condition both read as `email`, so the rule reported one of them as redundant. They serve different queries, `LIKE 'foo%'` and equality, and dropping either one loses something. A shared condition now groups only partial indexes that nothing else separates: b-tree, default operator class, valid, and with any expression intact. Measured on PostgreSQL 18.0.

- **The built-in formatter no longer writes statements that mean something else.** It split every multi-character operator and put a space inside it: `total >= 0` came back as `total > = 0`, `price::numeric` as `price : : NUMERIC`, `j->>'a'` as `j - > > 'a'`, and the same for prefixed literals (`E'…'` as `E '…'`) and exponents (`1.5e-3` as `1.5e - 3`). Most of those are syntax errors. Worse, a `--` comment swallowed the line after it: `where customer_id = 7 -- only this customer` over `and status = 'open'` came back with the second condition inside the comment, so an `UPDATE` formatted that way touches more rows. MySQL strings with backslash escapes (`'it\'s'`) were read as ending early, and everything after them was treated as inside-out. The tokenizer now reads tokens the way PostgreSQL and MySQL read them, and the formatter breaks the line after a line comment. The SQLFluff backend upper-cases keywords with the same tokenizer and gets the same fix. Proved three ways: an oracle over the format corpus in three styles (same token sequence, idempotent), the shapes run on PostgreSQL 18.4 and MySQL 8.4 before and after formatting with identical rows, and each lexer rule pinned on its own.

  **Upgrade:** if you ran `sqlens:format` with the built-in core (the `php` backend, or `auto` on a machine without pgFormatter and SQLFluff), review the diff it produced. Look for operators with a space inside them, a prefix separated from its string, and a `--` comment with code after it on the same line.

- **`auto` picks a backend that can express your style, not only one that is installed.** With `leading_commas: true` and pgFormatter installed, `auto` chose pgFormatter on PostgreSQL and SQLFluff on MySQL, and neither expresses leading commas, so every file came back `format_style_not_expressible` while the built-in core, which does, sat further down the list. The same project formatted fine on a machine without the binaries, and there `--strict-tools` failed it for missing two tools that could never have served its style. `auto` now takes the first installed backend that handles the dialect and expresses the style, names a missing backend only when it could have expressed the style, and when no installed backend can, keeps today's answer: the first installed one, which names the option. Measured with pgFormatter 5.11 and SQLFluff 4.3.0 installed.

  **Upgrade:** `Pushery\SQLens\Contracts\SqlFormatter` has a new method, `unexpressible(FormatStyle $style): array`, which `auto` asks before it chooses. A formatter you implemented yourself has to add it; return `[]` if it expresses every option.

- **`sqlens:format` no longer writes what pgFormatter or SQLFluff turned into a different statement.** An exit code of 0 was taken as proof, and both tools were measured writing broken SQL: pgFormatter 5.11 turns `U&'d\0061t'` into `U & 'd\0061t'` and joins the two lines of a Python function body into one, and SQLFluff 4.3.0 on MySQL splits `N'abc'` into `N 'abc'` and reads `5--1` as a comment, which it then moves in front of the `SELECT`. The output is now read back with the dialect's tokenizer and compared with the input. Lines, spaces and the case of bare words may change, `!=` may become `<>`, and a comment may move; any other difference leaves the file untouched and reports `format_tool_output_rejected`, naming the first token that changed. A function body in SQL or PL/pgSQL, and a `DO` block, is compared as code, so pgFormatter can still lay it out; a body in another language must come back byte for byte.

  **Upgrade:** a file that pgFormatter or SQLFluff used to rewrite into one of these shapes is now reported as undetermined instead, and in `--check` that moves the exit code. The detail names the token, so the choice is yours: format that file with another backend, or leave it as it is.

- **The pgFormatter backend formats the same way on every machine.** `pg_format` reads `./.pg_format`, `~/.pg_format` and an XDG config file unless it is told not to, and every option the backend does not pass came from there. Measured with a `.pg_format` in the working directory: `function-case=2` turned `count(id)` into `COUNT(id)`, `anonymize=1` replaced `'open'` with a random string, and `nocomment=1` removed the comment, all written back into the file. The backend now passes `--no-rcfile`. It also passes `--redundant-parenthesis`, because by default pg_format drops parentheses it considers redundant in DML (`where ((b = 1))` became `WHERE (b = 1)`) and a formatter here rewrites no expression. Measured on pg_format 5.11.

- **On MySQL, `uppercase_keywords` no longer renames a table.** The formatters upper-cased every word on their keyword list, and 21 of them are not reserved on MySQL and can name a table unquoted: `comment`, `transaction`, `date`, `text`, `view`, `begin`, `end` and more. `from comment` became `FROM COMMENT`, and MySQL on Linux (`lower_case_table_names=0`, its default) compares table names by case, so the statement named another table. On MySQL those words now keep the case they were written in; a reserved keyword is still upper-cased, and PostgreSQL, which folds unquoted names, is unchanged. The list was read off `information_schema.KEYWORDS` on MySQL 8.4.10, and the MySQL lane holds it against the server it runs on. The built-in core and the SQLFluff backend share the rule.

- **The built-in formatter keeps a two-word clause on one line.** Every clause keyword broke a line on its own, so `INNER JOIN` came out as `INNER` over `JOIN`, `DELETE FROM t` as `DELETE` over `FROM t`, a foreign key's `ON DELETE CASCADE` as `ON` over `DELETE CASCADE`, and the same for `LEFT OUTER JOIN`, `NATURAL JOIN`, `CROSS JOIN`, `ON UPDATE`, an upsert's `DO UPDATE`, `FOR UPDATE` and `COMMENT ON`. The statements were valid; the layout promised one clause per line. `OUTER`, `FOR` and `NATURAL` are now upper-cased keywords, and `NATURAL` starts its clause.

- **SQLFluff no longer refuses a valid statement over one line it cannot shorten.** When `sqlfluff format` finds a line it cannot break below `line_width`, it exits 1 with "Unfixable violations detected." and still prints the statement it formatted. The backend reported that as `format_tool_refused`, so a `CREATE FUNCTION` header longer than the width stayed undetermined and kept `--check` red for good. That exit is now taken as formatted, and the output still goes through the check that it reads as the same statement. A parse error, which exits 1 as well, is still a refusal. Measured on SQLFluff 4.3.0; `sqlfluff lint` names the rule, LT05.

- **The SQLFluff format backend formats.** It passed `--indent-unit` and `--indented-joins`, two flags `sqlfluff format` does not have, so every call ended with exit 2 and every file came back `format_tool_refused`. The backend now calls `sqlfluff format - --dialect … --nocolor` and carries `indent` and `line_width` as in-file directives after the statement, where a project's own `.sqlfluff` cannot override them and a parse error keeps its line number. `sqlfluff format` never changes keyword case, so `uppercase_keywords` is applied by the same tokenizer the built-in core uses. Measured on SQLFluff 4.3.0 for PostgreSQL and MySQL, with `indent: 2` and `line_width: 40`.

The value is declared, never probed: nothing on a server says how long it will live, and silence means persistent.

That covered two shapes worth judging. An index over `lower(email)` beside one over `(lower(email), placed_at)` is the ordinary redundancy case with an expression in it, and the second GIN index somebody added over the same column with the same operator class is the same index twice. Both were silent, and the silence was itself a finding elsewhere: an unjudged index over `lower(email)` is what covered an enumeration oracle in a consumer's schema.

The PostgreSQL reading asks `pg_get_indexdef()` per key position, so the list already says `lower(email)`, compares against `(email)` as the different thing it is, and the server normalizes the spelling on the way out: `LOWER(Email)` and `lower(email)` both come back the same, so two indexes written differently for one expression are recognizably one index without this package normalizing anything. What stays refused is an expression that does not ARRIVE — MySQL reports a functional index with no column name at all, and an expression holding a comma or a semicolon cannot cross the projection without being cut in half. Each of those says so in its own sentence rather than sharing one.

  **The method half is deliberately weaker than it could be, and the reason is measured.** Two indexes of one access method and one operator class are compared, and the only thing concluded is that identical column lists mean the same index twice. Not a prefix: a GIN index on `(tags, doc)` serves a query touching `doc` alone, so GIN coverage is a subset relation rather than a leading run — and an access method an extension supplies may be neither. This rule's advice is to drop an index, where being wrong costs a sequential scan on production, and identity is the one claim that holds whatever the method does with its columns. A partial index, an invalid one, and one whose reading was incomplete stay out of these groups entirely.

## [0.9.0] - 2026-09-08

### Added

- **The rule catalog has an introduction page instead of a generated list.** It explains what the parts of an id tell you before you open anything — `PG.L7.INDEX_REDUNDANT` reads as engine, level band, finding — which prefixes exist and what each one asks about, why `undetermined` is a third answer rather than a soft pass, and the five layers that can hide a finding, in the order they are applied.

  The links that reach it changed shape with it: a bare `rules/` is resolved against the URL, so on a subpage it points one level too deep the moment the documentation site serves paths with a trailing slash. They now name the file, which the site resolves itself and which our own contract test can check against the tree.

- **Two partial indexes carrying the same condition are compared with each other.** They cover exactly the same rows, so the predicate cancels and the columns decide — the same arithmetic as for two ordinary indexes. `PG.L7.INDEX_REDUNDANT` reports the narrower one, and it survives a difference in spelling: over a `varchar` column PostgreSQL prints `WHERE state IN ('open')` and `WHERE state = ANY (ARRAY['open'])` differently, and they are the same condition.

  ⚠️ **Two neighboring cases deliberately stay out, and both read like the obvious next step.** A *different* condition is an implication question — does `WHERE a IS NULL` cover `WHERE a IS NULL AND b = 1`? — and this release answers no such question. A partial index against an **unconditional** one is true as a statement about rows and wrong as advice: the partial index can be orders of magnitude smaller and somebody kept it that way on purpose, so dropping it is a loss rather than a tidy-up. Both are still reported as not compared, with the reason named.

### Changed

- **A partial index now says which condition went uncompared, instead of repeating the server's SQL back at you.** A partial index is still reported as not comparable, and no finding moves — knowing two predicates are the same condition says nothing about one covering the other, which is what a drop needs answered. What changed is the sentence: `partial index predicate not compared — it selects the rows where consumed_at is null: (consumed_at IS NULL)`.

  Four shapes are read: an inequality against a literal, a boolean test, a fixed set, a NULL test. Several of them have two spellings PostgreSQL prints differently over identical rows — `status IN ('a','b')` against `status = ANY (ARRAY['a','b'])`, `WHERE is_active` against `WHERE is_active = true` — and both spellings are read as the one condition they are. Anything else keeps the previous wording on purpose: a compound `AND`, a range test or a function call is reported as read-and-not-recognized rather than guessed at, because a guess would eventually name a condition the index does not have.

### Fixed

- **The published suppression order was backwards on both pages that describe it, and they disagreed with each other about how many sources there are.** One said three layers, the other four; the resolver applies five, and both put the **baseline first** where it is actually third. That is not a cosmetic disagreement: those pages promise to let you predict which layer a report will blame for a hidden finding, and either prediction was wrong.

  The order is `config`, `audit_ignore`, `baseline`, `annotation`, `destructive_opt_in`. The baseline losing ties is the design — it records findings somebody intends to fix and is meant to shrink, so a standing decision must never land on that burn-down list. Both pages now carry the order as a table, and a test reads the tokens back out and compares them against the resolver, in document order.

- **The documented CI recipe connected as a user that does not exist, to a database that does not exist.** Its `env:` blocks set `DB_CONNECTION`, `DB_HOST` and `DB_PASSWORD` and stopped. The `postgres` image with only `POSTGRES_PASSWORD` set serves user `postgres` and database `postgres`; Laravel's own pgsql defaults are `root` and `laravel`. `DB_DATABASE` and `DB_USERNAME` are now set, with a comment saying why they are not optional.

- **Two dead documentation links in the shipped rule evidence.** `MY.L7.INDEX_UNUSED` pointed at a MySQL manual page that has been dissolved rather than moved — 404 on 8.0, 8.4 and 9.x alike — and `SEC.PRIV.GRANT_SERVER_ADMIN` pointed at a `dynamic-privileges` page that is 404 in every version too. Both now point at pages that exist and that carry the fact the note claims: the table-wait summary reference, and the privilege reference that documents the SUPER split.

  Found by sweeping every external URL the shipped data carries, not by reading the two the report named. ⚠️ **One 403 in that sweep is deliberately left alone**: `blogs.oracle.com` answers 403 to a checker and to a browser alike, and its own index does too, so the host blocks us rather than the page being gone. Replacing a link on that evidence would be trading a working reference for a guess.

## [0.8.0] - 2026-09-08

### Added

- **A suppression may name a rule an external tool emits.** `sqlens.ignore` takes `SQUAWK.<rule>` and `PGLS.<rule>` now, including ids the shipped map has no row for — so you can silence one finding your installed binary reports without waiting for a release here. Before this, the only lever was `suppression.allow_undetermined: ['tool_rule_unmapped']`, which frees every unmapped tool finding at once, including the locking rules the tool is installed for.

  ⚠️ **No tool id was nameable before, not even a described one.** `ignore.rule` was checked against this package's own naming scheme, so `SQUAWK.ban-drop-table` — a rule the map does describe — was refused for its shape, while `PG.L1.NO_RULE_ANSWERS_TO_THIS`, a plain typo, was accepted. Two questions had one answer; they are separate now. How a rule of this package may be **called** is unchanged and just as strict.

  An id inside a tool's namespace that this build cannot describe reports `LINT.SUPPRESSION_TOOL_RULE_UNDESCRIBED` and the run continues. It is accepted, not waved through: nothing here can spell-check somebody else's ids, so the notice is what keeps a typo from silently un-suppressing nothing. An id outside every tool namespace is still refused.

- **`sqlens:lint` reports a suppression that names a deprecated rule, with the id that replaced it** — `LINT.SUPPRESSION_DEPRECATED_RULE`. Never an error: rules here are deprecated and never deleted, so the entry is still correct; it points at a check that will stop checking. The audit suite already named deprecated rules, but not which line of your configuration named one, and that line is the one you edit.

- **A rule can declare that your configuration has silenced it, through `DeclaresConfigurationReach`** — a new interface in the extension API. The level, category, stability and version gates decide whether a rule is in the set at all; this covers a fifth state they cannot express: the rule is admitted, it runs, and it can report nothing because a switch it reads is off. Only the rule that reads the switch can know, so only a rule that says so is asked — silence means "not examined on this axis", never "reachable".

### Fixed

- **`sqlens:lint` checks the rule ids in `sqlens.ignore`.** It did not. That form was validated by `sqlens:agent-rules` alone, a command a project may never run — so in the suite that fires on every migration, a typo silently suppressed nothing while the rule kept firing. A run now refuses an id no rule answers to, the same way audit always has.

  ⚠️ **Breaking for a project whose ignore list already carries a typo:** that run refuses instead of quietly linting. It is the direction the check exists for.

- **An `#[SqlensIgnore]` naming a rule that does not exist says so** — `LINT.ANNOTATION_UNKNOWN_RULE`. Nothing checked this form at all. The attribute takes a mandatory reason, which is what makes a broken one indistinguishable from a working one: it reads as a decision somebody weighed while suppressing nothing.

  Reported, and the run continues. Its config-file twin refuses, and the difference is where the text lives — an annotation sits in a migration that shipped years ago and will never be touched again, so refusing over a rule renamed since would turn your history into a timer.

- **Every `prefer-timestamp-tz` finding Squawk reports is mapped again.** All of them fell through as `tool_rule_unmapped`, at level 0, where a green run does not put them in front of you — measured in a consuming project at 47 of 47, with `0 fail` in the summary. The shipped map carried the rule under `prefer-timestamptz`, and the mapper joins on the name the binary **prints**. Squawk's own documentation page uses one spelling and its output the other, and it accepts both as an `--exclude` value, which is why nothing noticed.

  ⚠️ **A project that wrote `SQUAWK.prefer-timestamptz` into `sqlens.ignore` will now be refused.** That entry never suppressed anything, because the id could not appear in a report. The replacement is `SQUAWK.prefer-timestamp-tz`.

- **Every rule link on the published Squawk parity page reaches a page — all 39 were 404.** The map used `https://squawkhq.com/docs/rules/<rule>`; squawk documents one rule per page directly under `/docs/<rule>`. One link deliberately does not match its rule name: `prefer-timestamp-tz` points at `/docs/prefer-timestamptz`, because upstream's documentation slug and its printed id really do differ.

- **The published `config/sqlens.php` no longer names a test file you cannot open.** The comment on `deploy.postdeploy.budget_ms` said the number *is held by a test*, and named a path under the package's test directory — which never ships. It read as an assurance: raise the number and a red arm will stop you. None will, in your repository. The reasoning stays; the path is gone, and the comment says why.

- **The generated agent block no longer claims the catalog is what a run enforces.** It opened with *the rules this project actually enforces — what a run will check* over a single number. There is no single run: the catalog spans several suites and each command evaluates its own, so a consumer read **102 in force** while the linter in its gate checked **37**. And a rule can sit in that list unable to report at all — `PG.L9.DOC_MISSING_COMMENT` is admitted by the level gate and silenced by `audit.documentation.require_table_comments`, a contradiction inside the configuration that `--check` cannot see, because the artifact and the config agree with each other.

  The count now reads **Rules configured**. A **By suite** line says how many each suite carries, and says out loud that a rule in two suites is counted in both, so the numbers deliberately do not sum. Suite names rather than command names: `deploy` is reached through `sqlens:predeploy` and `sqlens:postdeploy`, so a command would have been invented. And a rule your own configuration has switched off says so on its own line, naming the key.

- **`DeclaresConfigurationReach` is named in the declared extension API**, where a third-party rule author can read it: in `ApiSurface::EXTENSION_CONTRACTS`, in the published API snapshot, and on the public API page. Without that it would have been a promise the breaking-change gate enforces and nobody could look up.

By maturity: 225 stable, 3 preview, 2 experimental. **151** answer to the level gate rather than to a severity axis of their own; the other **79** carry a severity — 7 critical, 32 high, 28 medium, 8 low and 4 info. The remainder are run notices and catalog-only rules, which the question does not apply to.

## [0.7.0] - 2026-09-06

### Added

- **`#[RawSql]` takes a second reason, `interpolation:`, for the case where the rule's own remedy does not exist.** `SEC.INJ.RAW_INTERPOLATION` answers an interpolated value with *pass it as a binding instead*, and for an IDENTIFIER there is no such thing: no engine binds a table, a schema, a partition or a constraint name, in DML or in DDL. A call site in that position could not answer the rule at all — what a project had was a PHPStan `ignoreErrors` entry, which carries no reason, so nobody later knows whether the line was considered, and is scoped by PATH, so the next interpolation in that file, one that DOES have a binding available, is silenced with it. Reported from a consuming project with seventy such call sites. The separation from `reason:` is the design rather than a detail: `reason:` answers why raw SQL was chosen and says nothing about a runtime value inside it, so letting it clear this finding would switch the injection rule off wherever the policy annotation is on — which is most annotated code, since that annotation exists to satisfy the rule beside this one. The two are independent in the other direction too: a `reason:` the run's policy refuses leaves an `interpolation:` standing, because they answer different questions. It reaches a class, a method, a function, a closure and an arrow function, with the same span rule the policy answer has. This package now answers its own rule the same way — nine call sites carry it, and the six-file exemption they used to need is gone. The bundled Boost skill documents it, including the half a reader needs most: where a binding does exist, bind it, because `reason:` alone deliberately leaves the interpolation finding standing.

### Fixed

- **A migration using `->change()` is judged, where it used to be read and then skipped.** Laravel's PostgreSQL grammar appends `comment on column … is NULL` to EVERY `->change()`, comment or not, and that statement form was not recognized — so one column change made the whole migration report `CAP.L0.UNDETERMINED_CAPTURE`, and nothing in it was checked. Measured in a consuming project over 56 migrations: three used `->change()`, three were reported uncanonicalizable, and the intersection was three of three. `->change()` is the Laravel spelling for the column rewrites and NOT NULL sets the lock-hygiene rules exist for, so the blind spot was the shape those rules are for, while the harmless `create` migrations beside it were judged cleanly. Recognizing the statement exposed a second half: `->change()` compiles to a COMPOUND alter, because the builder restates every modifier it was not told to keep, and `PG.L2.TYPE_CHANGE_REWRITE` handed that whole tail to its type matrix — so a bigint widening came back "cannot classify from the migration alone" rather than failing. The target type is read on its own now, and the cut is parenthesis-aware, so `numeric(10, 2)` no longer truncates to something the matrix cannot match. A `->change()` that rewrites the table fails; one whose retyping is free stays silent and still reports the `SET NOT NULL` the builder added on its own; a parameterized `varchar(255)`, which the target alone cannot settle, is still honestly undetermined.

- **A GIN index carrying a non-default operator class names the method as the reason it was not compared, not the class.** `AUDIT.CATALOG.UNREAD.NOT_UNDERSTOOD` reported `non-default operator class: jsonb_path_ops`, which points a reader at the operator class as the thing to fix. Measured against PostgreSQL's own `pg_opclass`: `jsonb_path_ops` is defined for `gin` and for no other access method, so an index carrying it is a GIN index by construction — and a redundancy question is only meaningful inside one method. Teaching the reader that class name would have rewritten the sentence and left the index exactly as incomparable, which is what a consumer proposed after reading the old message. The class is still named where it decides: a b-tree carrying `text_pattern_ops` serves `LIKE 'foo%'` where the default class does not, and those are two different indexes.

## [0.6.0] - 2026-09-06

### Added

- **`sqlens:lint --file` takes as many files as you name, which its own help had promised all along.** The option is declared repeatable, so Symfony ended its help line with *(multiple values allowed)* while the same line began *Lint exactly one migration file* — one sentence contradicting itself — and a second value was refused with exit 2. It failed cleanly, so the cost was time rather than correctness: a pre-commit hook over 53 staged migrations paid one artisan boot per file, measured at 0.58 s each. Resolved toward the capability rather than toward the narrower declaration, because a hook over several staged migrations is the use case the description itself names. The files are judged in the order they were named, and a path that does not resolve still ends the run before anything is linted — but the refusal now says WHICH file, which it could not while there was only ever one.

- **A new rule reports a `#[RawSql]` reason that no longer covers any raw SQL: `SEC.INJ.RAW_SQL_REASON_STALE`, at `info`.** The justification duty asked for a reason when the raw SQL was WRITTEN and nothing asked again afterwards — rewrite the call into a query-builder chain and the attribute stays, sitting on code that runs none, reading for the rest of the project's life as a decision somebody weighed. That is the shape that quietly empties an exemption table: every entry looks considered, so the next reader trusts all of them. A consuming project had built the two-way check by hand and could not retire it in favor of this package, because trading a two-way check for a one-way one is not adoption. A justification counts as live if ANY raw-SQL call site the suite collects is attributed to it — including a `DB::raw()` fragment or a dynamic identifier, which the policy rule itself stays silent about, because a reason covering one of those is doing its job. It says nothing under `policy: off` or inside an excluded path: a project that switched the duty off must not get findings about the annotations it wrote while it was on. The shipped registry holds 227 entries now — 136 safety and 58 security, 222 stable, and 79 carrying a severity at all: 4 info, the other 148 answering to the level gate instead.

### Fixed

- **A published `config/sqlens.php` that sets one nested key keeps every sibling the package ships.** The merge asked one question per TOP-LEVEL key, so answering `security.runtime_connection` froze the whole `security` block: `security.rls.mode` resolved to `null` although the package ships a default for it, and any key a later release adds under `security` would never have arrived. With a reference configuration of about 99 KB the only safe alternative was publishing all of it and diffing after every upgrade. A minimal file — the keys you are answering, nested as they are shipped — is the recommended shape now. Not through Laravel's `replaceConfigRecursivelyFrom()` either, and that is the half worth stating: it is `array_replace_recursive`, which replaces **lists by index**, so `['database/schema/*']` overridden with `[]` stays `['database/schema/*']` and `['a','b','c']` overridden with `['x']` becomes `['x','b','c']` — emptying a list would do nothing and shortening one would keep the package's tail, while `format.exclude` ships with an entry this package's own comments tell a project to empty. The rule instead: where the **package** ships a map, recurse; where it ships anything else, the published value wins whole, empty list included.

- **`#[RawSql]` now works where PHP allows it: on a function, a closure and an arrow function.** The attribute has declared `TARGET_FUNCTION` since it was written, so PHP accepted the annotation without a word — and nothing read it, because the collector visited class nodes only and a call site outside a class reports no scope name to join on. A free function is the ordinary shape for a test harness, and a **file-scope closure is every Pest test body**, which made the duty there not merely hard to discharge but impossible: the only remaining answer was an `exclude_paths` entry over the whole test tree, which silences far more than the finding. Those shapes are joined by POSITION now — everything inside the annotated function-like is covered, including a call one closure deeper, the same reach a method-level annotation has over its own body. A class or method annotation is unchanged and still joins by name. The finding's own message named only the method and the class, and now names the callable forms too.

- **`security.rls.mode = off` is now an answer the report can show, where it used to change nothing.** `SEC.RLS.DISABLED` closes its own remediation with *set the mode to off — that is an answer SQLens can record*, and until now a project that followed that sentence got the identical report: the same `undetermined`, at severity high, on every run. The cause was an ordering — the table scope was collected first, and `off` fell through the same empty list an unconfigured project produces, so nothing downstream could tell the two apart. The mode is read before the scope now, and the reading carries a third state: the rule answers with `not_applicable` saying this database separates nothing, and names what to change if that stops being true. It also unblocks a pipeline — `undetermined` escalates under `strict_undetermined`, which `--profile=ci` sets, so a project whose tenant separation lives in the query layer previously had to waive every undetermined at once to get a green run.

- **An unqualified name in `security.rls.tables` reaches the table it names.** The list matched only against `schema.table`, so a project that wrote `api_keys` — the name its own migration created the table under — got `not found in the catalog` for every entry: fifteen skips over fifteen tables that exist. The expensive half is quieter than the noisy one, because a security list matching nothing reports nothing and therefore looks configured. A bare name now resolves through `current_schema()`, which is where an unqualified `CREATE TABLE` puts a table rather than a guess about naming; a qualified one behaves as before. And the two ways of failing read differently: a bare name that resolves to nothing says so and suggests the qualified spelling, instead of describing a table that is missing.

- **A `sqlens:lint` run that judged no migration now says so, instead of exiting clean over nothing.** `--path` lints the PENDING migrations of a connection, and nothing is pending once they have all run — which is the state of every developer machine after `migrate` and of every pipeline that lints after its migration step, the place the check is most naturally hung because that is where a database exists. Measured in a consuming project: 56 migrations in the directory, 0 read, exit 0. The summary did say `over 0 migrations`, but the exit code — the half an automation reads — said what a run over all 56 would have said. Such a run now carries `LINT.NO_MIGRATIONS_READ`, a named undetermined derived from the COUNT of judged migrations rather than from a list of causes, so a cause nobody has enumerated reports as well. It joins the shipped registry as a safety entry — 136 of them — answering to the level gate rather than to a severity of its own. Under `strict_undetermined` — which `--profile=ci` sets — it moves the exit code; without it the run reports the finding and still exits clean, because a local run after `migrate` should not fail. The `--path` help on `sqlens:lint` and `sqlens:baseline` now says which set it reads, which it only implied.

- **`sqlens:lint --file=` no longer dies on a migration written in the old class shape.** Laravel accepts two shapes and the loader read one: a file that RETURNS an anonymous class. A file that DECLARES a named class returns nothing, `require` answers `1`, and the run ended with `resolve(): Return value must be of type Migration, int returned` — accurate, and about a private method of this package rather than the file it concerned. One such file in a project is enough to make the command unusable, and it need not be old code: `vendor:publish` wrote that shape for years, so a published migration nobody has touched since carries it. The fix needs no new derivation — once the file has been required the class IS declared, so the same reflection-checked lookup that came up empty a moment earlier now finds it. A file that is neither shape, such as a class whose name no longer matches the file it lives in, is refused by `UnloadableMigration`, which names the file and what it handed back.

- **Each published remediation schema now carries its own `$id`.** All three — v1, v2 and v3 — identified themselves as v1, and `$id` is the key a JSON Schema validator caches a loaded document under. Load two of them into one registry and you keep whichever arrived last, so a `schema_version: 3` payload could be validated against v2, whose `strategy` enum is closed and has never heard of `reindex_before_refresh`. Nothing about validation changes: the documents differed in what they constrain and were identical only in what they called themselves, so every payload accepted before is accepted now. The URLs those identifiers use do not resolve to a page, which is allowed — a `$id` is a name, not a link — and they are unique names again.

## [0.5.0] - 2026-09-05

### Added

- Catalog rules can now carry fix material. A second contract, `ProvidesSchemaObjectRemediation`, takes the schema object a rule just judged — the existing seam takes a canonicalized statement, and generalizing it to a union would have made that form's guarantee conditional rather than adding a case to it. Two acts, two contracts, each with the guarantee it can actually give. The payload declares `subject: schema_object`, so the fields that mean nothing about a state a database is already in are refused rather than rendered. `MY.L2.NO_PRIMARY_KEY` is the first rule to answer on the catalog side, with the same considered `none` its statement half reaches: putting a key on a populated table needs a candidate that is unique and NOT NULL across every row, which is a fact about your data that SQLens never reads.

- Seventeen of the eighteen catalog safety rules now carry fix material, where none did. Twelve are server settings and their answer was already written — `AbstractServerSettingRule` has said for months what changing one costs, derived from whether it takes a reload, a restart, or a new cluster; it is a payload now instead of a sentence appended to a message. The rest are considered `none`s carrying the rule's own conclusion: putting a key on a populated table, or moving a money column off a binary float, needs a fact about your data that SQLens never reads. None of them proposes a migration for something no migration can change — a template telling you to set `data_checksums` is advice you would follow for an afternoon before finding out it is fixed at `initdb`.

- **The eighteenth completes the set, and it cost a schema version: the payload is now version 3.** It was `PG.L5.COLLATION_VERSION_MISMATCH`, and its sequence needed a strategy the enum did not have: `REINDEX` first, then `ALTER COLLATION … REFRESH VERSION`. The order is the whole of it — refreshing first tells the server the recorded version is current while every index is still sorted by the collation's old rules, which silences the warning and leaves the wrong answers in place. `strategy` is a closed enum in the published document, so the new value is a version of its own: a consumer validating a version-3 payload against the version-2 document would reject it on a value that document never described. Version 2 stays in the package unchanged, beside version 1. The completeness gate counts catalog rules like everything else now, and the named exclusion that said they were structurally out of reach is gone rather than merely empty.

- Fix material for a state finding now reads like one. The renderer says "in a new migration" where a statement's template says "in a later migration" — the second quietly implies an earlier one, and for a finding that came from reading your database there is none. It takes the distinction from the payload's `subject`, never from a shape it recognizes, so there is one answer to that question rather than two that can drift. A state finding's verification line also names the right command: `sqlens:audit` confirms the state afterwards, while `sqlens:lint` judges the migration before it runs — two commands, two moments.

- The extension API is enumerated and diffable. The public-api page has always promised "the interfaces a third-party rule package implements" without ever naming them, so a signature change on one reached you with nothing red in between — the snapshot compared rules, exit codes and schema versions, never a method. All nine are now named in `ApiSurface::EXTENSION_CONTRACTS`, the published snapshot carries each one's method signatures, and the breaking-change check forbids a move in either direction: an interface has no benign one, because adding a method breaks every implementer and removing one breaks every caller. The declared list is held to what rules actually implement by a derived arm, so a new capability interface cannot ship unpromised and a promise cannot outlive the thing it describes. `ProvidesSchemaObjectRemediation` ships `preview`, like the payload it produces.

- `sqlens:format` gains `--format=console|json|github` and positional path arguments. `json` and `github` go to STDOUT, so `--format=json > report.json` yields a file holding nothing but the document, while the console verdict and every degradation notice stay on STDERR. An unknown value is a misconfiguration and is refused before a single file is rewritten, never a quiet fall back to `console`. Past GitHub's ten-per-level cap the run says how many it withheld and which, because a truncated list that does not say so reads like a shorter one.

- `sqlens.format` gains the discovery keys `paths`, `exclude` and `extensions`, which decide which files a run may find. Roots default to the application's migration paths exactly as before, so a project that configures nothing behaves unchanged; the command line still wins over a configured root. `exclude` takes globs and defaults to `['database/schema/*']`, because `schema:dump` rewrites those files from the database anyway — a project that hand-maintains its schema file empties the list, and the run then names the dump files it touched, so the decision is visible in the output rather than only in a config file. `extensions` widens the set to other files that hold nothing but SQL. `php` and `phtml` are reserved and cannot be added: a Laravel migration is a PHP file, and reading one as SQL rewrites the whole file as a single statement, so the value is refused by the config validator and dropped again at runtime. `vendor/`, `node_modules/` and `storage/` are never walked into, symlinks are not followed, and the order is byte-wise so it does not move with the ambient collation.

- Every entry in the shipped rule registry now declares an `attribution`: `authored` when the finding names something you wrote and can rewrite, `observed` when it names what the run found in the world — an unreachable server, a lock another session holds, an index whose build died. It is what decides whether an entry owes a bad/good example pair, and the classification means something in both directions: an authored entry without a pair cannot ship, and neither can an observed one that carries a pair for a migration nothing causes. 159 of the 225 entries are authored, 66 observed.

- `explain_rule` now answers with the ten capture examples, which live on their producers rather than in the bundled register. It read the register alone and reported `registered: false` over examples that exist and are good — including every pre-scan finding, where the example is exactly what turns the rule id into something an agent can act on.

- Two deploy checks gained example pairs: `DEPLOY.LEGACY.CONSTRAINT_NOT_VALIDATED` and `DEPLOY.LEGACY.CONSTRAINT_NOT_ENFORCED`. They are the only two in that family that a migration causes and a migration avoids — the other twenty-two describe the environment the run found, and a pair for one of those would be confident, concrete, and about something else.

- The remediation payload gains a `subject` discriminator: `statement` for a template that rewrites a statement you wrote, `schema_object` for one describing a migration that does not exist yet. It is emitted on every payload, including the default, so you read the shape from the document instead of inferring it from which rule produced the finding. A `schema_object` payload must not carry a `downtime_class` — there is no deploy whose effect it could describe, and one that carries it is refused rather than rendered.

### Changed

- **The remediation payload is now schema version 2, and version 1 is frozen where it was.** `subject` is the only field that moved, but it moved in a way version 1 cannot absorb: the version-1 document is strict, so a consumer holding the copy that shipped with 0.1.2 through 0.3.0 rejects a payload carrying the new key, and requiring the key means the version-1 document in this package rejects a payload written before it. Both would have claimed to be version 1 — the one state the field exists to prevent. Read `schema_version` and treat a number you do not know as a payload you cannot use; that rule was already the documented one and is what makes this a bump rather than a break. `resources/data/schemas/remediation-payload-v1.schema.json` stays in the package unchanged, so an archived payload can still be validated against the contract it was written under, and every version-1 payload is a `statement`. `remediation_schema_version` in the API surface moves with it, which the breaking-change gate already classifies as allowed in a minor while the payload is `preview`.

- Every `sqlens:format` run now also states whether strict tool mode was on. The line already named the backend, its version, the dialect and the style fingerprint; the strict flag is the remaining parameter that changes what a run *does* rather than how it formats — with it on, a backend the run could not use is a failure, and without it the run says so and carries on. Two machines that exited differently over the same files usually differ there, and the line now shows it instead of leaving it to be guessed. It is printed in both states, unlike the tool version, which is omitted for the built-in core because its absence already says the core produced the output.

## [0.3.0] - 2026-09-05

### Added

- `#[NoSqlOnDriver]` says where a migration's emptiness is deliberate, so `CAP.L0.NOT_CAPTURABLE` stops reporting a decision you already made. A migration that emits nothing on one driver — a partial index is a PostgreSQL feature, a storage-engine change means nothing outside MySQL — annotates the method or the class with the driver and a reason, and the rule stays quiet on exactly that driver. It still reports on a driver you did not name, so the attribute cannot become a blanket switch that merely sits closer to the code, and a misspelled driver name excuses nothing anywhere, which is how the typo shows up instead of quietly disabling the check. Unlike a baseline entry, it moves with the file when you rename it, it sits where the decision was made rather than in another document, and it stops applying the moment the migration becomes empty for some other reason. The reason is required; an empty one is treated as though the attribute were absent.

- A formatter backend can now be asked which version of itself is installed, without formatting a file first. `SqlFormatter::version()` returns the installed version, or `null` when the question cannot be answered — the binary is absent, or it did not respond to the probe. It never throws: a backend is something that improves the output, never something a run requires, so asking about a missing one must not be what fails. The built-in PHP core answers with the package's own version rather than `null`, because it ships inside the package and cannot be missing, and `null` would put the one backend that always works in the same column as the ones that are not installed. Asking repeatedly costs one probe: the answer is a fact about the machine, identical for the first file and the two-hundredth.

### Changed

- **If you implement `CaptureRule` yourself, `appliesTo()` now receives the run's `SubjectContext` as a second argument.** Some capture questions depend on which driver the run is on, and the answer has to exist before a finding does — `evaluate()` must return one, so a rule that decides in there that it should stay quiet has no way to say so.

- **If you implement `SqlFormatter` yourself, you now need a `version()` method.** The interface is the seam behind which a custom backend plugs in, so adding a method to it is a change your implementation has to follow. Returning `null` is a valid answer and the right one when you cannot determine a version.

## [0.2.0] - 2026-09-04

### Added

- `format.binaries.<backend>` takes a third answer: `false` says this project does without that backend. It is a decision rather than a gap, and the run treats it as one — the backend is not named as something that would have been added, and `--strict-tools` has nothing to fail over. A backend that is merely absent is still a loss and still fails a strict run, because the machine that has it formats differently and the output is committed. Naming a switched-off backend is refused rather than substituted, with a message pointing at the key. The built-in core cannot be switched off: it is what makes the suite work with no binaries at all.
- The interpolation rule now reads what the engine's own escaping did to a value, and treats the two forms differently because they are not equally strong. `$connection->escape($value)` is `PDO::quote()` — the result is a value literal that cannot change the statement's grammar or select a different object, which is what a binding gives you at a position that accepts no binding, so the finding goes. `$connection->getQueryGrammar()->wrap($name)` is **not** the same guarantee: measured against both shipped grammars, it stops the breakout (`x"; DROP…` comes back quoted and doubled) and not the object choice (`other_schema.secrets` comes back as two quoted segments). So that finding stays, and only the advice changes — from "pass it as a binding", which no engine accepts for an identifier, to constraining the value to a set you wrote. `wrap()` around a `DB::raw()` is refused outright: an `Expression` is handed back verbatim, so the argument must be provably a string.

- The console summary now names the denominator behind its counts: `summary: 0 fail, 4 undetermined, 0 suppressed — over 32 migrations`. Every number on that line was a numerator, and a numerator alone cannot separate "nothing was wrong" from "almost nothing was read". A consuming project met exactly that: `--path=database/migrations` lints one directory level — because that is what Laravel's own `getMigrationFiles()` globs, so `migrate --path=` does not run the nested migrations either — and a tree of 32 central and 298 tenant migrations reported a clean run and exit 0 over 32 files. The behavior is Laravel's and stays; what was missing was any way to see it. A run whose producer has no file list to count, such as `sqlens:audit`, states no number rather than a misleading zero.

### Changed

- `security.include_vendor_migrations` now decides whether a run READS a package's migrations, not only how it classifies them once it has. Off — the default — a `sqlens:lint` run no longer loads or pretend-executes a migration that ships inside `vendor/`, so a first run after `composer require` can no longer fail on findings inside another package's migrations while reporting nothing about the project's own. The switch keeps its old meaning as well; the setting is one question asked one step earlier. Two runs are deliberately not filtered: one whose paths you named (`--path`, `migration_paths`, `--file`), and `sqlens:predeploy`, because a package's migration really does run during a deploy and can take a lock like any other. If every pending migration turns out to be a package's, the run reports `LINT.SKIPPED.ONLY_VENDOR_MIGRATIONS` rather than an empty result that would read as clean.
- The interpolation finding now names what to do when no binding form exists. An identifier, a schema name, or DDL assembled from an enum takes no placeholder in any engine, so `statement('… = ?', [$value])` was advice that could not be followed there — and with `analyse.exclude_paths` deliberately not reaching the injection rules, a project that could not find the alternative was left with turning the rule off or turning the analyzer off. The alternative existed all along in PHPStan's own `ignoreErrors`, keyed on the rule's identifier and scoped to a path; it is now named in the finding itself, in `extension.neon`, and on both documentation pages. The identifier is derived from the rule rather than written by hand, and a test drives the real analyzer to prove the block removes exactly those findings and leaves every other rule reporting.
- The rule page and the bundled example register both claimed every method the rule looks at takes a bindings array. `DB::raw()` and `DB::unprepared()` do not, and the page's list of fragment methods was also missing `raw`. Both now say what the sink register says.

### Fixed

- A `#[RawSql(reason: …)]` whose reason was wrapped across lines silently answered nothing. Only a bare string literal was read, so `'a ' . 'b'` — the way PHP wraps a sentence, and the way a reason worth writing usually has to be written — left the finding standing while looking exactly like enforcement. Literals joined with `.` are now read as one reason. A constant or a variable anywhere in the expression still refuses the whole of it: reading one would mean evaluating project code during analysis, and that decision is unchanged.
- A derived run context silently lost its `guard_profile`. `RunContext::copyWith()` took the value as a parameter and never passed it on, so every context derived through `withDriftMode()` and its siblings reported a run with no guard profile — a legal state, and therefore invisible from the outside. Found while adding a field beside it, in the one field no test compared.

- `#[RawSql(reason: '…')]` did nothing on an anonymous class, so it did nothing in a Laravel migration — the form every migration has taken since Laravel 9, and where raw DDL usually lives. The rule's own message recommends the attribute, and the only remaining answers were to turn the rule off or to exclude the migrations directory, both of which silence more than the finding. The collector was skipping any class without a namespaced name, which an anonymous class never has; it now joins on the name PHPStan gives it, which is the same name the call site reports. Both placements work: on the class and on the method.

- A database whose name contains `livewire` was read as a production connection, so every database-creating mode refused to run against it — in `local`, and with `--force`, because the production check sits above both. The marker `live` matched it as a segment prefix, and naming the database after the application is what Herd, Valet and `laravel new` all produce. `livewire` is now recognized as a coincidence rather than a marker. The exemption is for that segment alone: `livewire_production` is still production, and every name the obvious alternative cure would have dropped with it — `livedb`, `proddb`, `liveserver` — is still caught. The detector can also name the segment and marker behind a verdict now, so the reason no longer has to be found by removing one segment at a time.

- The shipped config comment for `connection` said `null` means the framework's default connection, full stop. True for capture and lint, and false for `sqlens:audit`, which deliberately does not consult `database.default`: with more than one supported connection it refuses and lists the candidates, because which instance was read is part of what the report asserts and a primary and its replica disagree about settings, about lag, sometimes about schema. A project meeting that refusal had no way to anticipate it from the file it had just configured. The comment now states both halves, and one test reads the block out of the shipped file while driving the resolver, so the prose and the behavior cannot drift apart again.

## [0.1.0] - 2026-09-03

The first public release. Nothing before it ever shipped, so there is no earlier version for any of this to be a change *from* — read the sections below as a description of what the package **is**, not as a diff.

### The shape of it

SQLens is a database safety toolkit for Laravel applications on PostgreSQL 18+ and MySQL 8.4+. It reads the migrations you are about to run and the schema you already have, and it says what they will cost.

Three principles govern every part of it, and they are worth stating first because they explain most of the design decisions further down.

**No silent green.** Every result is one of three values — `pass`, `fail`, `undetermined` — never two. A check that cannot run is reported as `undetermined` with a named reason, never folded into the passing set. On a managed database, where a great deal of the catalog is simply not exposed to any role you can hold, that third value is the normal answer rather than an edge case, and a tool that hid it would be reporting a clean bill of health for questions it never asked.

**Primum non nocere.** The tool must not harm the database it is pointed at. It takes no lock of its own, issues no write, and reads catalog and state views only. It sets its own session timeouts so it cannot become the thing that hangs. It keeps no state in your database at all — the migration debt account is a file in your repository, not a table. The two modes that do create a database create a throwaway one, and both sit behind a production guard that refuses by default.

**Determinism.** The same state produces the same result on a developer's machine and in CI. That is held by the `assume_server_version` pin, strict tool mode, and a canonicalization layer every rule works on rather than raw SQL. There is deliberately no "fast" path that disagrees with a "correct" one.

### Added

**Eleven commands.**

- **`sqlens:lint`** — reads the migrations that have not run yet and reports what they will do to a live database. It obtains their SQL through Laravel's own grammar rather than by parsing your migration source, so the advice is about the statement your app will really send: by default without executing it (`--pretend`), or by running it against a throwaway shadow database it creates and drops itself (`--shadow`). `--roundtrip` replays up, down and up again in that shadow database to test whether `down()` is a real inverse. A single-file fast path (`--file`) needs no database at all and is built for a pre-commit hook.
- **`sqlens:audit`** — reads the catalog of a database that already exists and judges the schema as it stands. It will not guess which connection, which read host, or which tenant the report is about: where the configuration leaves a choice, the run stops and says so rather than describing one server under another one's name.
- **`sqlens:security`** — roles, grants, transport, server configuration, row-level security, injection and unencrypted columns, across every suite. Gated by a severity axis of its own rather than by the strictness level, so lowering the level band cannot silence it.
- **`sqlens:predeploy`** — reads the target database immediately before a deploy: read-only, fail-closed, and bounded by a time budget so it can never be the thing that hangs a release. It checks what the migration is about to walk into — a lock blocker, replication lag, disk headroom, a missing privilege, a read-only target, a version skew.
- **`sqlens:postdeploy`** — reads what the deploy left behind: an index that ended up invalid, a constraint that was never validated, an orphaned transition object. Read-only, catalog-only, once.
- **`sqlens:drift`** — compares what the database holds against what the migrations describe, with an exclude file for the differences a project has accepted, each needing a reason.
- **`sqlens:baseline`** — writes the findings of today into a file you commit, so a project can adopt the tool on a schema it inherited without a red build on day one.
- **`sqlens:format`** — one house style for the SQL in your migrations, with a `--check` mode a CI step can act on and a `--diff` mode that shows what a write would do without doing it. Three backends behind one seam; the built-in one needs nothing installed.
- **`sqlens:doctor`** — what SQLens can actually see from here: each connection's real server version, and each optional tool's version or its absence. An absent tool's line names what you lose by not having it rather than merely reporting it missing.
- **`sqlens:mcp`** — serves the same engine the commands use to an AI agent over stdio. Every tool is read-only unless named individually with `--enable-tool`; there is deliberately no option that enables them all.
- **`sqlens:agent-rules`** — writes the project's active rule set into its coding agents' context files, so an agent knows a rule before it writes the migration rather than after the linter rejects it. Opens no database, and its `--check` mode treats a missing artifact as a deviation rather than creating it.

**225 rules, every one of them documented.** The catalog ships as a data artifact with a published page per rule id, and the count is held rather than claimed: 225 entries, 225 pages, zero pending. Every finding carries the URL of its own page, derived from the rule id rather than written by hand, so a link a shipped finding already carries cannot drift.

By category: 135 safety, 57 security, 17 idiom, 7 performance, 6 convention, 3 privacy. By maturity: 220 stable, 3 preview, 2 experimental.

**Ten cumulative strictness levels, and the level is an appetite rather than a severity.** Level 4 runs everything up to 4. The distribution is deliberately front-loaded — 136 rules sit at level 0, and the bands above it add taste rather than danger. Level 6 tells you about choices a reasonable engineer might have made on purpose, and reading that band as a defect list is the commonest way to misread it.

**A maturity axis that keeps a minor release from breaking your pipeline.** A new rule lands as `preview` and runs only on request. An unconfigured project gets stable rules only — the opposite default to categories, where unconfigured means all, and the difference is the point: an unset category axis means nobody expressed a preference, an unset maturity axis is the versioning promise doing its job.

**A `downtime_class` on every finding that can change a statement's locking behavior** — `online`, `blocking` or `rewrite` — so a deploy script can ask whether this release needs a maintenance window without knowing which rules carry the answer. 58 entries carry one: 38 rules and 20 deploy checks, distributed 38 online, 18 blocking, 2 rewrite. The rest carry none because the question does not apply to them — a run notice describes the run, and a rule that only reads the catalog is not about a statement that takes a lock. The JSON envelope exposes the worst one in the run directly rather than making a consumer re-derive an ordering that is this package's judgment and is not alphabetical.

**A severity axis of its own.** 78 of the 225 entries carry a severity: the 58 security and privacy rules, which answer to it instead of the level gate, plus 19 deploy checks and one debt notice, where a severity orders several failures rather than gating any of them. Across all of them: 7 critical, 32 high, 28 medium, 8 low, 3 info. The other 147 entries answer to the level gate. The two gates are never merged — a strictness choice and a security risk are different facts, and one number cannot carry both.

**Five reporters over one result** — console, JSON, GitHub annotations, SARIF, and an agent format — plus registration for a custom one. The SARIF output is validated against the real schema rather than eyeballed, over a populated run, an empty one and a catalog-only one.

**A four-value exit-code contract** a pipeline branches on: clean, findings above the gate, misconfiguration, and undetermined under strict mode. Misconfiguration beats everything, including a run with no findings at all, because a tool that cannot trust its own setup must never report green.

**A pre-scan that refuses to execute a migration it cannot execute safely.** A migration that sends mail, calls an HTTP endpoint, guards on introspection, or reaches its effect through your own code is reported and never pretend-executed. Recognizing a side effect is not the same as preventing one, and the honest move is to decline rather than to run it and hope.

**A migration debt account.** The two-step patterns this tool recommends — expand then contract, add then validate — leave a second step somebody has to actually take. The ledger is a file in your repository that records which ones are outstanding, how long they have been, and which have since been resolved. It is a repository file rather than a table on purpose: a safety tool that writes to the database it is auditing has given up the property that makes it safe.

**A supported-version floor that qualifies the report instead of withholding it.** Below the floor the run still produces its findings and says unmistakably what they are worth — a named `undetermined`, a marker in the run header, and a failing exit under strict mode. The message states that findings may be wrong in both directions, because the one-sided reading misses the dangerous half: below the floor no rule was ever written for the hazards that only exist there, so a clean report is the least informative result the tool can produce rather than the best one.

**A bundled Laravel Boost skill**, so an assistant working inside a consuming application has the adoption guidance without being told where to look.

### Security

The package connects to production databases and shells out to external binaries, so its own posture is part of what it ships rather than an implementation detail.

- **It takes no lock of its own, and writes nothing to the database it is pointed at.** Every read goes to a catalog or state view. The two modes that need to execute a migration — `--shadow` and `--roundtrip` — do it in a throwaway database they create and drop themselves, never in yours, and both refuse to run against a production connection unless the guard is explicitly lifted. The one network call in the package is `sqlens:security --refresh-advisories`, which is never a side effect of a check and runs before anything connects.
- **Credentials are redacted from every output** — reports, the JSON envelope, the agent artifacts and the debt ledger.
- **The MCP server is read-only by default.** A mutating tool is exposed only by being named, one at a time.
- **Database-creating modes sit behind a production guard** that refuses by default and reports which of its three checks held a blocked run, because the three need different fixes.
- **A dedicated read-only audit connection is supported**, so the role that reads your catalog need not be the role your application runs as.

### What 0.1.0 does not do

- **The public API is not frozen.** It is documented, and it is what a 1.0 will commit to, but a field or a flag may still change in a minor release before then.
- **PostgreSQL and MySQL only.** MariaDB is refused by name rather than half-supported: it answers Laravel's `mysql` driver and does not share its semantics, and the divergences are exactly what this tool reasons about — so advice about it would be confident, specific, and about another product. SQLite and SQL Server are declared non-goals for the same reason.
- **One shipped locale.** Everything this package emits goes to a terminal, a CI annotation, a SARIF file or an agent artifact, and a translated `ALTER TABLE` warning still contains `ALTER TABLE`.
- **Statistics-dependent rules are opt-in and honest about it.** The index-usage rules answer from counters that can be reset, so they ship `experimental` and report nothing until you ask for them. The source-reading pre-scan detectors ship `preview` for the same reason.
- **Levels 8 and 9 are thin** — 4 and 6 rules. The convention band is defined and only lightly populated.
- **The MCP server cannot shield standard output from what precedes it.** It takes the channel as early as a service provider can, diverts stray writes to the diagnostic stream and keeps `stdout` for protocol frames — but a message PHP emits while loading a file happens in the autoloader, before any provider boots. A host application whose dependencies emit a compile-time deprecation can therefore corrupt the frame stream, and no code inside the server can intercept it. The client reports a protocol error; the cause is on the other side of the boundary.
